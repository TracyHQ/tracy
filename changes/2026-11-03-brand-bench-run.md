- **Brand bench run: a command-line script runs the brand step (prompt v10, verbatim) over two new model doors, with its own tables, a one-at-a-time queue and a 1 USD cap per run** — Claude, for Akemi · #320 · `feat/brand-bench` · 2026-11-03
  **Affects:** ops admins and whoever runs the benches. `node scripts/brand-bench.mjs` (`kits`, `run`, `list`, `status`, `get`, `cancel`) queues a brand run from a brief file or a brief revision and a template kit; the worker in the tracy-web process runs it in parallel with planner runs. Two doors are added to the catalogue and to the `llm_assignment` check (migration 195): **Brand agent** (requires tool calls and reading pictures) and **Brand reviewer** (requires reading pictures); they are assigned in /ops like any door, have no environment fallback, and a run is refused when a door is unset, disabled or incapable, when both resolve to one model, or when a brand door holds an Anthropic model. Migration 196 adds `brand_run`, `brand_round` and `brand_call`, apart from the planner and WO tables. Every model call is logged with tool, model, purpose, status, latency and cost (never a key or image bytes), the cost is split agent / drawing / reviewer, and a run may spend 1 USD, checked before every call. A gate rejection goes back to the same conversation listing only the rejected fields (two fix rounds at most, each tagged agent or gate fault); then, or at the cap, code builds a safe version and marks the run `safe-version` with the reason. A call dispatched and never answered is not sent again after a redeploy (the run fails with the reason). No route, screen or API change.
