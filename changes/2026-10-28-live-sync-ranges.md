- **Sync from live reads a big table that moved range by range: only the ranges that changed** — David (Claude) · #17 · `perf/live-sync-ranges` · 2026-10-28
  **Affects:** owners of imported sites pressing Sync from live, Preview or Send, once their site's Claude Cowork plugin answers `db.range_checksums` (TracyHQ/claude-cowork#248, not released yet). A table of 2 MB of dump and more that the live read takes whole (`lib/live-pull.mjs`) is cut into ranges of its rows by its one integer key — about 512 KB, at most 2 000 rows each — and the site's checksum of each range is kept beside the read (`<dump>.ranges.json`, kept and forgotten with the base by `webroot-sync.sh`). When the table moves, the next read asks for the same ranges and reads again only those that moved, keeping the last read's rows for the others; the result is the table a whole read would bring (the same rows in key order, headed by the site's CREATE TABLE now — the same digest). WordPress read `wp_postmeta` (135 000 rows, 15 s) and `wp_posts` (26 MB) again for one edited title, and again for an edit lock just to compare. A count that does not add up, a key out of its range, most of the table moved, an engine without the action, or a write the checksums around the read catch: the table is read whole, as before.
  **Deploy debt:** the fleet scripts ship in the `tracy-host` image, rebuilt on merge to `develop`; production with the next `develop` to `main` release. Nothing changes on a site until its plugin carries the engine actions (a claude-cowork release).
