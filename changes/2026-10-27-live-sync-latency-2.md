- **Sync from live and Sync to live read the live site once and less of it, and load reads side by side** — David (Claude) · #PR · `perf/live-sync-latency-2` · 2026-10-27
  **Affects:** owners of imported sites (Joomla, WordPress) pressing Sync from live, Preview, Send or Undo. The tables the merge never takes from the live site (`lib/live_sync.py never-taken`: Tracy's own, such as the Claude Cowork engine's undo log, and the ignored ones, such as sessions, Smart Search's index and plugin logs and queues) keep the last read's part instead of being read again, on both platforms; when only they moved, the read is "nothing new". The engine's undo log (22 MB on a WordPress test site) was read again after every Send or Undo, and Joomla passed no ignored tables at all. The live read's dump is one gzip member per table with `<dump>.index.json`: an unmoved table is copied byte for byte instead of unpacking and packing 60 MB again (15 s on WordPress). When WordPress's row comparison finds a real change, the tables it read are the read's own (`wp_postmeta` was asked for twice). Live reads load into scratch schemas over several connections (`tracy_db_load_dump`, `dump_sections.py split`); a dump with views, routines, a tail, `LOCK TABLES` or no `-- table` line loads in one, as before. A push kind whose key or filter names a column one side lacks is left out instead of stopping the changeset with `ERROR 1054`.
  **Deploy debt:** the fleet scripts ship in the `tracy-host` image, rebuilt on merge to `develop`; production with the next `develop` to `main` release. The first sync after deploy reads as before once (no index yet), then uses the index.
