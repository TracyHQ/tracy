- **A newcomer can follow `docs/running-locally.md` to a working stand, and a macOS stand can create sites again** — open-source agent U · `os/w3-newcomer` · 2026-10-27
  **Affects:** anyone running the local stand on macOS, and anyone running a second stand on one Docker. Since per-site network isolation (`fe42c564f6`) only tracy-web joined `<label>_default`; on macOS tracy-host is not host-networked, so provisioning could not reach the new site and every new WordPress site failed with "WordPress never finished copying its core … after 180s". `lib/site-network.sh` now also joins this stack's tracy-host when it sits on the shared network (macOS only; servers are unchanged), and `teardown.sh` lets go of both. `deploy/scripts/check-local.sh` loads `deploy/compose.override.yml` on macOS (plain compose already does on Linux), checks the stack's own network (`<project>_tracy`) instead of always `tracy_tracy` (it used to advise removing another stand's network), and reads `TRACY_HOST_PORT`/`HOST_DNS_PORT` from `deploy/.env`. `docs/running-locally.md` gains the missing steps (jq, host networking, `/ops/cms` snapshot, seeding `TRACY_DSH_HOME`, first-run `dns-host`), a DeepSeek key note, how to make a site while the quickstart releases are private, how to run a second stand, and how to package the desktop app for your own server. Three gates that were red on the line are green again: `questions` (canonical file synced with its mirror), `emdash-inventory` (regenerated), `vocabulary` (hooks README heading; the export overlay `SYSTEM.md` sits outside the coined-word scope like the root file it becomes).
  **Build debt:** the site-network fix ships in the `tracy-host` image; a macOS stand needs `up -d --build tracy-host`.
