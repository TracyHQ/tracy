- **A new isolated EmDash site on a host-networked tracy-host is no longer refused as "a bridged tracy-host" while its web container is still starting** · Claude, for the Tracy team · #410 · `fix/emdash-provision-wait-loopback` · 2026-11-05
  **Affects:** whoever provisions EmDash sites on a fleet host (dev, any `network_mode: host` tracy-host). `_emdash_prepare_site_network` (`platform/emdash.sh`) asked the site's published loopback port once, right after `docker compose up`, and treated a refusal as "this host is bridged"; the port refuses for about 1.5 s after a start, so installs of `tracy-restaurant/emdash-0.x` failed ~15 s into setup with "cannot identify this bridged tracy-host". Now a host whose HOSTNAME is not a container id (the machine's name: host-networked) waits up to 90 s, polling about twice a second, for the port, and when it never answers says "isolated site did not answer on 127.0.0.1:PORT within 90 s". A host whose HOSTNAME is a container id (a bridged tracy-host, whose loopback is its own) still asks once and goes straight to the unchanged identity and network checks, so it does not wait. The reachability check on the site's private address after a temporary network join waits the same way. Other platform scripts and the later `_emdash_site_origin` probes were read and left alone: a failed loopback probe there falls through to the site's network address, it does not refuse. Test: `emdash-post-up.test.mjs` (isolated fleet cases); regression case `REG-PR-410-emdash-provision-wait-loopback`.
