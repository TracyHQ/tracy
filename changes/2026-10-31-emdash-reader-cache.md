- **An EmDash site keeps its Content API source rows in memory while its database is unchanged, so a second read costs no whole-site scan** — bug-fix agent (emdash-reader-cache) · #PR · `perf/emdash-content-reader` · 2026-10-31
  **Affects:** EmDash templates Base 0.5.8, Business 1.7.25, SaaS 1.4.16 (`tools/content-api`) and the vendored kit copy. `identity-sqlite.mjs init|fork` (run by `platform/emdash.sh` at provision and restore) now adds the table `_tracy_content_changes` and three counting triggers per watched table to the site database; sites keep reading fresh until that step has run with the new template. Customer sites get it only from a template release (`~/TCH-local/bugfix-1030/RELEASE-EMDASH-READER.sh`, prepared, not run) or `redeploy-template.mjs` followed by `identity-sqlite.mjs init`. Includes the kit's v1.5.3 list-item reader (2,027 to 119 native calls), byte for byte, so it merges cleanly with `perf/agent-tool-calling`.
  **Measured:** Business seed (2,000 records, 40 locales) in a local container: one id read 0.77 s median with 2,027 native calls before; 0.31 s on a miss (120 calls) and 0.008 s on a hit (0 calls) after; 41 id reads after a write 1.57 s in total. Answers on a hit are byte-identical to the miss before them.
