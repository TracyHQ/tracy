- **A Joomla provision fetches the contract profile through the GitHub API asset route when the plain release download fails, and /ops shows the fetch's own reason** — Akemi0x · `fix/joomla-contract-fetch-github-fallback` · 2026-11-08
  **Affects:** every Joomla quickstart provision and demo update whose Claude Cowork component (0.24.55+) fetches its profile at provision (`joomla-contract-fetch.php`). The provisioner now hands the component's `ContractFetch` its own downloader: the same `PackageDownload` size and sha256 checks, 120 s instead of the door's 15 s, and one retry through `api.github.com/.../releases/assets/<id>`. A failed fetch now prints `!! contract-fetch: ...`, which `failureReason` reads, so the demo card names the reason instead of "not on disk". Nothing to rebuild by hand: the next host image carries the script.
  **Why / Measured:** the JA Voyara 1.0.12 demo update failed within a minute with only `contract profile ja-voyara/j6/1.0.12: not on disk`. The same script, the same Claude Cowork 0.24.90 package and the same web image fetched the profile fine afterwards, so the cause on the host is not visible from /ops (the fetch's own line was hidden by the shell's line after it). The github.com release download route had answered 504 for whole Claude Cowork releases earlier the same day (quickstart.py's fallback covers the parts; the profile fetch had none). With the plain route forced to 504, the real 0.24.90 component fetched the 1.0.12 profile through the API route (manifest sha256 matching the pin).
