- **Shards update again and build their own Joomla site images: the installer writes `MINIO_PASSWORD`, the `tracy-host` image carries the Joomla skill tree, the updater builds missing site images on every update, and shard update alerts are told once per target tag** — Dai Nguyen (Claude) · #TBD · `fix/shard-minio-joomla-skill` · 2026-10-28
  **Affects:** every shard and whoever installs one. Since `deploy/compose.yml` requires `MINIO_PASSWORD` (compose interpolates the local-only MinIO services on a server too), a shard env without it fails every `docker compose` call, so every update; `install-shard.sh` now writes `MINIO_PASSWORD=no-minio-runs-on-a-shard` (fixed, not a secret), and a shard installed before this change needs that one line added to `/etc/tracy/tracy-web.env` by hand. The `tracy-host` image grows by about 66 MB (`vendor/joomla/joomlart-t4-skill`, lifted to `/opt/tracy-fleet/vendor/joomla/` by `sync-fleet-files.sh`), and `web/build.sh` builds the Joomla images from there when there is no checkout; from a checkout (CI, the master) it runs as before. `joomla.Dockerfile` is unchanged on purpose: its bytes are in the `tracy.web.inputs` label, and any edit would make `build.sh` refuse every Joomla image already built. The updater now runs `web/build.sh` whenever `web/IMAGE_TAGS` names an image the host lacks, not only when the file changed (a failed run had already put the new file in place, so later runs never built the missing images), and lists each missing image once. On the master, `shard.update_failed` and `shard.web_images_missing` are each told once per (shard, target tag) instead of once per hourly retry, and `shard.web_images_missing` only for an update that succeeded. Merged code reaches shards only with the next `tracy-host` and `tracy-web` images; the master's alert change needs the next master deploy.
