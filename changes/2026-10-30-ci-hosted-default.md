- **Tracy CI on a pull request runs on GitHub-hosted `ubuntu-latest` by default, with the full workers suite in three rows there; the label `ci:self-hosted` puts a pull request back on our runners** — hano-xbt (Claude) · `ci-hosted-default` · 2026-10-30
  **Affects:** whoever opens, reads or merges a pull request. A same-repository pull request now runs `dsh-lib`, `plan`, every `build-check` row, `full suite skipped`, `test growth` and `new-test proof` on `ubuntu-latest` without any label; `ci:hosted` (#221) no longer means anything. To run on our runners instead, set `ci:self-hosted` BEFORE the push or "Ready for review" (read from the event payload, like `ci:aws-only`). Nightly and manual runs stay self-hosted; fork pull requests still get only `fork pull request checks`. When the full workers suite runs on GitHub-hosted it is `build check (tests 1/3)`, `(tests 2/3)`, `(tests 3/3)` instead of `(tests 1/2)`, `(tests 2/2)`; the clock-shift step and `rest` ride the last shard. A release pull request into `staging`/`main` therefore shows the three rows, and `check-pr-merge.mjs` requires them when the run's `plan` job and rows ran GitHub-hosted (two on our runners), and both it and the full-run proof of `green-tree.mjs` refuse a run whose plan job and rows ran on different runner kinds, or whose row set is the other kind's.
  **Shards balanced on what they run (both runner kinds):** `check-tests.ts` now leaves the skipped database files out BEFORE splitting the workers shards (a file's shard may differ with and without the skip; it is still in exactly one), and on GitHub-hosted (`TRACY_TESTS_HOSTED=1`, set by `Build check`) preloads the last shard with the hosted cost of the small suites (`HOSTED_COST`: 464 s `rest` + 9 s clock tests, from run 41028805223) instead of the table's 185 s. The owner tasks of the Turbo rows are unchanged.
  **Timing table:** checked in the code — `update-test-timings.mjs` read ONLY `pull_request` runs into `develop`, so with pull requests on GitHub-hosted (three shards, refused) and skipping the database files it would have stopped learning. It now also reads the nightly (`schedule`: our runners, two shards, every file), recorded in `source.runs` with `pr: null` and `headSha` = the `develop` commit the nightly pinned and tested, read from its own log (a scheduled run's `head_sha` is `main`'s); a nightly whose log does not name that commit exactly once per job is skipped. The committed table is not refilled here (no `gh` login); the next `node --import tsx scripts/update-test-timings.mjs` can use nightly runs.
  **Why / Measured:** to take pull-request load off our runners (Hano's decision). On run 41028805223 (hosted, warm) the two shards took 8 m 51 s–12 m 39 s and 19 m 45 s–20 m 50 s, against 9 m 30 s and 13 m 43 s on our runners. Forecast slowest row (not measured yet): hosted PR 11 m 01 s (was 20 m 50 s measured on two rows), hosted full run 15 m 42 s, self-hosted PR 11 m 02 s (was 13 m 09 s forecast), self-hosted full 16 m 46 s unchanged — model and table in `docs/references/gates-ci-runners.md` › Runners. Our runners keep two shards, since their check pool is shared with image builds.
