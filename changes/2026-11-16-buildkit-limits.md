- **The CI image builders (`tracy-$RUNNER_NAME`, docker-container) now run at most 4 build steps at once (`max-parallelism = 4` in `buildkitd.toml`) inside a container capped at 8 GB of RAM with no swap on top (`--driver-opt memory=8g`, `memory-swap=8g`).** — Fleet maintainers · #649 · `buildkit-limits` · 2026-11-16
  **Affects:** both image workflows, through `.github/actions/buildx-builder`. The cap is in the create flags, so it is part of the config hash: the first image job on each runner after merge recreates that runner's builder once (`::notice` "Image builder replaced"), cache volume kept. Builds take longer when more than four steps could run at once. At the cap the kernel reclaims the builder's page cache first; a build that really needs more than 8 GB of anonymous memory now fails its job (OOM inside the builder) instead of the host's OOM killer picking a customer site.
  **Why / Measured:** 16/11 on the dev host (8 CPUs, 31 GB) the builder had `HostConfig.Memory=0`, `NanoCpus=0`; its cgroup `memory.peak` over two `build-app-images` runs (one rebuilding all 8 web images) and two `build-dsh-image` runs was 7363 MiB, mostly page cache (afterwards anon 167 MiB, file 3.0 GB). Locally (buildx v0.38.1, BuildKit v0.34.2, Docker 29.9.2): the created container has `HostConfig.Memory=8589934592` and `MemorySwap=8589934592`, `buildx inspect` lists the four GC rules and `max-parallelism = 4`, and a second run reuses the builder. `scripts/test/ci-buildx-builder.test.mjs` 11/11.
