  **Affects:** ops users of tracy-web. Runs are started and read with `node scripts/site-planner-bench.mjs` inside the tracy-web container (`kits`, `run`, `list`, `status`, `get`, `cancel`); there is no screen, route or API endpoint, so the API snapshot does not change. A new model door `sitePlanner` (`/ops` › Model & AI) must be assigned before a run starts: by default the `deepseek` provider with `deepseek-v4-pro` (text only, so the kit needs a current `look` for every page and block shot, or the start is refused), or the OpenRouter provider with `anthropic/claude-sonnet-5.5` (reads each `look` and opens a kit image only when a look cannot settle a decision); the door now requires tool calls and only prefers vision; WO doors are unchanged. Migrations 188 to 190 add the door to the door check and the tables `site_planner_run`, `site_planner_round` and `site_planner_turn`. The worker runs inside the tracy-web process, one run at a time. The first run on a kit version downloads its `template-kit-*.zip` from the quickstart release (releases credential) and caches the images under `TRACY_READINESS_DIR/site-planner-kit-images`; a kit whose images do not match is refused before any model call. New shared module `apps/tracy-web/src/lib/agent-over-door.js` runs a tool loop over a door and knows nothing about plans or kits.
