- **The site planner bench runs on the server on DeepSeek Flash: a command line starts a run, a background worker runs the approved planner prompt as a tool-using agent that reads the kit's text looks, and the checker scores each plan with up to two fix rounds** — Claude, for Akemi · #301 #302 #303 · `feat/site-planner-bench-run` · 2026-11-03
  **Affects:** ops users of tracy-web. Runs are started and read with `node scripts/site-planner-bench.mjs` inside the tracy-web container (`kits`, `run`, `list`, `status`, `get`, `cancel`); there is no screen, route or API endpoint, so the API snapshot does not change. A new model door `sitePlanner` (`/ops` › Model & AI) must be assigned before a run starts. The default is `deepseek-flash` on the `deepseek` provider (profile `deepseek-flash-native`, reasoning effort high): it reads each page and block `look` (the plain text of its 1440 shot, from the template kit) with tool calls and opens a kit image only when a look cannot settle a decision. Alternatives that still run: `deepseek-v4-pro` on the `deepseek` provider (text only, so the kit needs a current look for every shot or the start is refused; it gets the whole kit in its first message and no tools), and `anthropic/claude-sonnet-5.5` or `anthropic/claude-opus-5.5` on the OpenRouter provider. The door requires tool calls and only prefers vision; WO doors are unchanged. Migrations 188 to 194 add the door to the door check, the tables `site_planner_run`, `site_planner_round` and `site_planner_turn`, and the columns for retries, change lists, `site_planner_turn.progress` and `site_planner_run.balance`. The worker runs inside the tracy-web process, one run at a time. The first run on a kit version downloads its `template-kit-*.zip` from the quickstart release (releases credential) and caches the images under `TRACY_READINESS_DIR/site-planner-kit-images`; a kit whose images do not match is refused before any model call. New shared module `apps/tracy-web/src/lib/agent-over-door.js` runs a tool loop over a door and knows nothing about plans or kits. Calls on DeepSeek's own API are streamed: a call with no byte for 3 minutes is cut and retried, DeepSeek's overload answers are retried, and `status` shows the call in flight as a `call` line; OpenRouter calls are not streamed. A fix round answers with a list of changes: the valid ones are applied, only the invalid ones are sent back once for correction, and only then is the whole plan asked for. A run that reads with tools is told to write after 20 reading answers or a read of parts it already had, and every run stops past 2 USD (`SITE_PLANNER_BUDGET`). DeepSeek turns are costed at DeepSeek's published peak or off-peak price by UTC dispatch time, and a DeepSeek run stores the account balance before and after, shown by `status` and `get`.
  **Why / Measured:** the planner and checker were approved outside the repo (ADR 0041). Three dev runs on one invented brief and the same frozen checker chose the default: DeepSeek Flash at effort high took 10.5 minutes and about 0.04 USD, 62 failures in the first draft and none at the end; at effort low it took 7.6 minutes but left 202 failures in the first draft and 2 after the last fix round; DeepSeek V4 Pro (text only) took 33.5 minutes and about 0.41 USD with 186 first-draft failures. Tests drive the bench with an invented brief, a fake GitHub, fake kit zips and a scripted fake model; no real model is called in tests.
