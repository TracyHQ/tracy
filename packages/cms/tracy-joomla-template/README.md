# @tracy/joomla-template — `tpl_tracy`

One Joomla 5/6 site template whose look is a **parameter**: any of the 152 OpenDesign design
systems vendored in `vendor/tracy/od-design-system`, plus a navigation and a hero layout. Not a dsh
plugin; nothing here runs in the harness. The zip goes onto a customer's Joomla.

## How the look is chosen

A template *style* (Joomla's own concept: one template, many parameter sets) carries three look params:

| Param | Values | Default |
|---|---|---|
| `inspiration` | id of a design system (`brutalism`, `airbnb`, `apple`, …) | `default` |
| `nav` | `auto` · `top-left` · `top-centered` · `brand-centered` · `sidebar` · `overlay` | `auto` |
| `hero` | `auto` · `split` · `centered` · `cover` · `stack` | `auto` |

`auto` takes the archetype recorded for that design system in `inspirations.json`. `index.php`
resolves the three (`resolve.php`), loads `media/css/inspirations/<id>.css` after `tracy.css`, and
stamps `<body data-inspiration data-nav data-hero data-page>`. `layout.css` does the rest, so
switching the style changes the whole site without touching content.

A fourth param, `motion`, is not a look param and `resolve.php` never sees it: it holds the motion
effects the site has switched on, as the one JSON string the agent writes. `index.php` parses it and
only a non-empty list registers `tracy-motion.css` / `tracy-motion.js` and includes
`motion-head.php`; missing, empty or unparseable means every effect off and not one extra byte. All
three of those files are generated by `packages/cms/tracy-cms-motion` — read them there.

`tracy.css` is written once against the 56 token names every design system declares and has no
`:root` of its own. The design system's file is the only source of colour, type, spacing, corners
and shadows.

## Generated files — do not edit

`scripts/build.mjs` derives these from the vendor library and commits them; `--check` is a gate:

- `src/tpl_tracy/templateDetails.xml` from `templateDetails.tpl.xml` (version, the 152 options)
- `src/tpl_tracy/inspirations.json` (id → name, category, nav, hero, dark)
- `src/tpl_tracy/media/css/inspirations/<id>.css` ×152 (each system's `tokens.css`, verbatim)
- `src/tpl_tracy/media/css/fixtures/<id>.css` ×152 (each system's `components.html` stylesheet,
  fenced under `.tracy-fixture`)
- `src/tpl_tracy/media/css/artifacts/<kind>/<id>.css` ×456 (the brand engine's landing, form and
  typography for each system, fenced under `.tracy-artifact`)

```
pnpm --filter @tracy/joomla-template build     # regenerate + dist/tpl_tracy-<version>.zip
pnpm --filter @tracy/joomla-template check     # exit 1 when a generated file is stale
pnpm --filter @tracy/joomla-template test
```

The build refuses a system that drifted from the 56-name contract, so a re-pinned upstream that
renamed a token stops here rather than shipping a template with holes.

## Content contract — what a seeder writes

The layouts render the four page kinds of `docs/agents/design-preview.json`:

| Kind | Joomla | Fields |
|---|---|---|
| `home` | article with `attribs.article_layout = "tpl_tracy:home"` | `attribs.hero_eyebrow`, `hero_headline`, `hero_sub`, `hero_cta_label`, `hero_cta_url`, `hero_cta2_label`, `hero_cta2_url`; image in `images.image_fulltext`; body in `fulltext` |
| `listing` | category blog (menu item type *Category Blog*) | one article per item: `title`, `images.image_intro`, first tag or category as the kind |
| `article` | article, default layout | `title`, `publish_up`, author, `images.image_fulltext`, `introtext` (lead), `fulltext` |
| `pricing` | article with `attribs.article_layout = "tpl_tracy:pricing"` | body holds `<table class="tracy-pricing" data-hot="N">`; `tracy.js` marks column N |
| `page` | article with `attribs.article_layout = "tpl_tracy:page"` | title, then the body — a plain page, or one whose body is a section of the library (Style guide, Contact) |
| `landing` | article with `attribs.article_layout = "tpl_tracy:landing"` | the body alone, no title — a page built from the section library, which opens with its own hero (`sections/landing.html`) |
| `fixture` | article with `attribs.article_layout = "tpl_tracy:fixture"` | `fulltext` = the output of `tracy-cms-sections/scripts/fixture-body.mjs <id>`; the page loads only `fixtures/<id>.css` |
| `artifact` | article with `attribs.article_layout = "tpl_tracy:artifact"` and `attribs.tracy_artifact = landing\|form\|typography` | `fulltext` = the output of `artifact-body.mjs <id> <kind>`; the page loads only `artifacts/<kind>/<id>.css` |

The layout is chosen by the article's `attribs`; a menu item must not force `layout=` in its
link, or it overrides the article. The stand's home is the `artifact` landing — it carries its own
navigation and calls to action, so it stands as a front page — and the `fixture` sits at
`/design` in the menu.

A design page (fixture or artifact) loads the stylesheet of the system its body was written for
(the wrapper's `data-inspiration`), not of the current style: switching the style in the admin
restyles every section page and leaves the design pages as they were, instead of putting one
system's stylesheet on another's markup. Bringing them over is a rewrite of their body. Menu: a `mod_menu` module in position `nav` with a
`#__modules_menu (id, 0)` row.

## Trying another design system from the address bar: `?style=<id>`

Any page with `?style=brutalism` (any id in `inspirations.json`) renders in that system for this
visitor: the token file, and the nav and hero layouts the system comes with. The choice is kept in
a `tracy_style` cookie for a day, so following links keeps the look; `?style=` with no value
forgets it. An unknown id is ignored. Design pages (fixture, artifact) keep their own system —
their markup is per system. Nothing is written to the database: this is a preview, and the admin's
style stays what it was.

Caches: a previewed page answers with `Cache-Control: no-store`, so proxies and CDNs do not keep
it. Joomla's own page cache (System - Page Cache, off by default) keys a page on its URL alone, so
a `?style=` URL is cached correctly on its own key — but a cookie is not part of the key, and a
page rendered for one visitor's cookie would be stored for everyone. With that plugin enabled the
template therefore neither sets nor reads the cookie: the preview lives in the URL only. Joomla
has no `nocache` URL parameter; the hook for cookie-dependent pages is a `pagecache` plugin that
adds the cookie to the key (`onPageCacheGetKey`), which this template does not ship.

## Language files are named `tpl_tpl_tracy`

Joomla derives a template's language file name as `tpl_<element>.ini`, and this template's
element (its folder) is `tpl_tracy` — so the files are `language/en-GB/tpl_tpl_tracy.ini` and
`tpl_tpl_tracy.sys.ini`, installed into the site's `language/en-GB/`. The admin's Edit Style form
derives that name on its own and cannot be told otherwise; with the files named `tpl_tracy.ini`
the site rendered translated while the form showed raw `TPL_TRACY_*` keys. The keys inside keep
the `TPL_TRACY_` prefix.

## Local stand

```
node scripts/build.mjs
docker compose -f dev/compose.yml up -d          # joomla:6-apache + mariadb:11, port 8080
docker compose -f dev/compose.yml exec -T db mariadb -uroot -ptracy-dev joomla < dev/seed.sql
dev/demo.sh brutalism | airbnb | apple           # switch the style and print the checks
```

Admin: `http://127.0.0.1:8080/administrator`, user `tracyadmin`, password in `dev/compose.yml`.
`down -v` to start over — the image only installs on an empty volume.

## Where it is released — not to the registry

This package is `private` and is **never published to npm.tracy.ai**. Nothing imports it: the
template is not a dependency, it is a zip a Joomla installs. Publishing it would create a second
address for the same files and no reader would know which one a site is running.

The one public address is the distribution repository,
[TracyHQ/claude-cowork](https://github.com/TracyHQ/claude-cowork) — the same repository the Cowork
package comes from:

```
node scripts/sync-cms-themes.mjs <claude-cowork>  # mirror src/tpl_tracy → joomla/template/tpl_tracy
# then, in that repository:
node scripts/release-joomla-template.mjs 0.1.1    # tag, zip, GitHub release, update.xml entry
```

`templateDetails.xml` declares that repository's `joomla/template/update.xml` as the template's
update server, so a site finds a newer version under Extensions → Update. Joomla records the
address at INSTALL time: a site that installed the template before this line existed has no update
site and must be updated once by hand.

A site being built installs the same released package: `tracy-site-build`'s `theme` stage reads the
first `<downloadurl>` in that file and runs `joomla.php extension:install --url=<url>`. **The lane
image carries no copy of the template.**
