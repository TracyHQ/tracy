## 五分钟内你能做什么

1. 在你持有席位的 Site 的 **Settings → API keys** 中创建一个 API key。
2. `GET /v1/me` —— 查看这个密钥以谁的身份行事、作用于哪个 Site、拥有哪些 scope。
3. `GET /v1/sites/{key}/pages` —— 列出该 Site 已发布的页面及其内容 id。
4. `PATCH /v1/sites/{key}/records/{kind}/{id}` —— 修改一个标题，并记录在一个 `apply_id` 之下。
5. `POST /v1/sites/{key}/applies/{apply_id}/revert` —— 把它恢复回去。

[快速开始](/zh-cn/quickstart/)用 `curl` 逐一演示了这五次调用。

## 系统是如何组织的

```text
Bearer trk_…  (you, your agent, a partner's integration)      cookie tracy_sess (a browser on cowork.*)
      |  /v1/*  — Bearer only, no cookie                              |  /api/sites/{key}/apply, /api/me/keys
  api.tracy.ai ── API host ── allowlist ──┐                           |
                 └─ /docs/api/<document>   (this site: docs.tracy.ai) |
                                          ▼                           ▼
                        applyDoor(siteKey, action, params, principal)   ← ONE path: seat · effective permissions ∩ scopes · lease · audit
                                          |
                  Claude Cowork plugin (Joomla, WordPress) · Tracy reader (EmDash)
```

- **`api.tracy.ai`** 只响应 `/v1/*` 和 `/docs/api/` 下的三份机器可读文档（OpenAPI、Claude Cowork 插件、llms.txt）。本文档站和交互式参考位于 **`docs.tracy.ai`**。除此之外别无他物：登录、workspace 和 Ops 工具都在 Tracy 自己的主机名上，在这两个主机上一律回答 `404 NOT_ON_THIS_HOST`。
- **只有一个入口。** 每条 `/v1` 路由都是 Apply 入口（Apply door）某个动作的薄别名——与 Tracy agent 走的是同一条路：你是谁（密钥的所有者）、你的席位允许什么、Site 的写入租约（lease），以及审计日志。
- **由 Site 作答。** 在 Joomla 和 WordPress 上，调用会到达安装在该 Site 上的 Claude Cowork 插件；在 EmDash 上，则由 Tracy 自己的读取器处理。Site 拒绝的内容会以文档化的[错误](/zh-cn/reference/errors/)形式返回给你。
