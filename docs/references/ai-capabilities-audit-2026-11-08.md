## Product boundary

Tracy helps a person change a real website through an agent. Site changes, Diff, Undo and Backup are the trust mechanism; chat is the way to ask. There is no approval step before an agent change. The supported platforms are WordPress, Joomla and EmDash. These statements come from `CONTEXT.md` and govern the proposals below.

## Priority 0: acceptance gaps that affect the customer's site

1. **A brief-built site may still contain demo identity or unsupported claims.** Two pilots and the scope of issue #189 describe demo pictures, incomplete replacement and facts that did not come from the business. The existing single-agent build can stop partway through. The acceptance target is a whole handed-over site with no demo residue, invented people/prices/numbers, wrong-offering pictures or broken links, including phone and desktop views. Track #189, #192–#198 and #231. Do not treat the replacement step chain as evidence of a corrected customer outcome until its end-to-end cases pass.
2. **The new step chain still needs a completed customer acceptance Build.** Planner, writer, picture and write benches exist, and PR #488 connected them for business-link builds after the original audit. The PR description records defects found in a local chain run: missing logo media, demo portraits left visible, false dead-link results and disputed slot ownership that stopped a write. Complete #482 acceptance, then repeat on a WordPress and an EmDash quickstart before enabling either CMS broadly. Track #472, #479, #482–#484 and PR #488.
3. **A formally valid input can be semantically wrong.** Brief media labels and template slot roles determine what the agent chooses and writes. The open readiness specs require the labels to be judged against actual content, not merely present. Measure source, person, offering, subject and frame labels on real briefs and rendered template pages before admitting a template to the chain. Track #37, #38 and #376.

## Priority 1: consistency, cost and recovery

4. **EmDash writes could proceed after the write-lease door failed — fixed locally in this PR.** `packages/tools/tracy-site-tools/src/host/index.ts` `emdashWriteLease` returns `null` for a missing session or plan and logs then proceeds for any answer other than Stop or `SITE_BUSY` (around lines 3219–3246). This preserves compatibility with older `tracy-web`, but a live web outage can allow two conversations to write without serialization. This PR adds an unavailable-door case, refuses unconfirmed leases, retains the intentional `SITE_BUSY` wait and updates `SYSTEM.md`. Deploy the matching web lease door before the rebuilt dsh image; local tests verify the refusal path, while a real EmDash site acceptance run remains to be done.
5. **A bench budget is checked after answered calls; unknown-cost continuation is fixed locally in this PR.** `agent-over-door.js` now refuses the next model call of a budgeted run with `AGENT_BUDGET_UNKNOWN` when an answered call has no known cost, including after resume. Unbudgeted runs continue as before and the cost ledger still marks unknown calls separately. One call can still cross the budget before its answer returns; measured call-level overshoot and an upper-bound reservation remain open. Coordinate with #478 and whole-build cost work in #480.
6. **Stop is honored between model turns, not during a call in flight.** The `agent-over-door.js` contract states this explicitly. In-flight model work can continue after a user or operator stops a bench. Bound request time and avoid replay of ambiguous write outcomes; measure the time and cost from Stop to actual termination. The site-editing agent's stopped-write receipt already addresses a different, related case and should be preserved.
7. **Output quality of a picture can be below a passing looker verdict when a frame cannot be hidden.** The picture fallback may keep the best picture rejected for minor faults so a required frame is not empty (change journal, 6 November). Carry `filledBy` and its fault names into the final site report and review a stratified sample by frame role. A hero, person or offering picture needs a stricter acceptance policy than decoration. Track #336 and #194.
8. **Template and plugin readiness must be an admission rule for the chain.** Missing contract doors, stale content maps, missing baseline measurements or unreleased plugin pins cannot be repaired by a prompt. The readiness verdict detects many cases, but the operational policy for already-live releases differs from a new Publish. Build a CMS × release × plugin-door matrix and only enable chain builds where the required read and write contracts pass. Track #429, #452 and the readiness sections of `SYSTEM.md`.
9. **The write step needs full-site idempotence and read-back.** Open issues cover creating planned pages, hiding every planned item, stable reruns, page settings, link targets and printed alts. An unchanged rerun should produce no new Site changes entry and no demo content on kept pages. Test the complete site, not only a mapping export. Track #352–#379, particularly #374, #375 and #379.
10. **Repair needs an exact fault list and a bounded scope.** The post-write site agent should receive only remaining site-check faults, change only those sites/pages/slots, and be scored by before/after findings. An unresolved finding must remain visible at handover. Track #197, #477 and ADR 0044 section 30.

11. **Effective model readiness is not established by an unassigned door.** The live `/api/ops/llm` response had no assignments for six doors of the proposed Build chain. Source permits an unassigned door to use an environment fallback, so absence of a row is not proof of failure. Add an admission check for each enabled chain step that resolves its effective provider/model and performs the required capability test, including picture looker vision. Record the result per deployment and template before turning on the chain. Do not call the chain ready solely because the ops page and provider entries load.

## Priority 2: assistant and observability

12. **`/help` streaming admission is per process.** `apps/tracy-web/src/assistant/route.js` uses a local `Map` and `MAX_STREAMS_PER_ACCOUNT = 2`. This is an actual per-process bound, not an account-wide bound across web instances. Confirm the deployment topology; if several instances serve the door, use shared admission or state the chosen per-instance policy and load-test it.
13. **`/help` attachments are not read by the model; the disclosure is fixed locally in this PR.** The route sends only file names, types and sizes, and `assistant/prompt.js` explicitly tells the model it cannot open their content. The creation chat composer now shows this limit whenever a usable file is attached, in all eight interface languages. A request to answer from a document still requires a separate content-reading feature and permissions; this change does not claim that Help can read attachments.
14. **Telegram staff identity depends on configuration.** With support enabled and an empty `CS_TELEGRAM_STAFF_IDS`, the assistant route logs that every member of the support group can reply as staff. The audited source does not establish the live configuration. Verify every deployment; if the group is not the intended trust boundary, require staff IDs or disable the staff reply path when empty.
15. **The cost and time of one complete Build need a common record.** Individual benches and Website Opportunities have partial ledgers. PR #488 proposes per-step minutes and USD, a deadline and an ops row. Verify retry cost, unknown cost, drawing cost and total time against a real run; compare failure and cost distributions by CMS/template rather than optimizing a single example. Track #480 and #481.
16. **AI account fallback needs outcome measures.** The routing code can switch to Tracy AI after the customer's connection fails. Count switch reasons and whether the next turn succeeds; test quota, authorization, timeout and network cases. Keep the note about the answering model separate from the agent's site permissions and write capability. The live account has no connected provider, so this path was not exercised.
17. **Model-translated template blurbs need language review.** The background translation checks retained terms and length, which are useful structural checks but do not establish meaning or natural language quality. Sample high-traffic blurbs across offered languages and record corrections. `SYSTEM.md` describes the translation path.
