# Gates, CI and runners

Moved verbatim from §6 of [`CLAUDE.md`](../../CLAUDE.md) on 29/09/2026. Only relative paths and § references were changed for the new location.

## Gates

`pnpm build:check` runs **forty-three gates** (counted 24/09 — the **authoritative list is `scripts/check-all.ts`**; count there, not in this table); it runs every selected gate and then lists all that failed. The list is explicit on purpose: a new `scripts/` file runs only once a line in `check-all.ts` enrols it; a gate dropped from the list stops running with nothing saying so. Each gate script opens with why it must be a machine and not review — read that before changing a gate.

| Gate | Catches |

A gate that stands itself down when a condition is missing reports the same green as one that ran — the fail-open shape this repo refuses everywhere.

### test:clock-shift — run tests with the clock moved 400 days ahead

Not a gate of `check-all.ts`: this is a test RUN (`scripts/run-clock-shift.mjs`, preload `scripts/clock-shift.mjs`; tests: `scripts/test/clock-shift.test.mjs`, `scripts/test/run-clock-shift.test.mjs`).

**Why it exists.** `beta-operation-signal.test.mjs` minted a session cookie at a fixed clock of 01/10/2026 02:00 UTC and then sent it to a door that asks `viewer()`, i.e. verifies against real time. A session lives 72 hours (`SESSION_TTL_S`), so the test was green until 04/10/2026 02:00 UTC and then red on every run of every PR: four red CI runs before #838 fixed it by minting that cookie at real time. On the day it was written, no diff showed this bug. Running that same test "400 days later" shows it at once, without needing to know how the test was written.

**Convention for fixtures:**

- A credential used in an integration test is minted with the clock of whoever verifies it. A door that reads real time → `mintSession(email, secret)` with no time argument.
- An expiry test passes the SAME clock to both the minting and the verifying call (`verifyBetaToken(token, secret, clock + 7 * 86400_000)`), or computes from real time (`Date.now() - 73 * 3600 * 1000`).
- Fixed dates in general are not banned. Only one shape is red: a fixed minting time, verified against real time.

**What the preload does.** It moves `Date.now()`, argument-less `new Date()` and `Date()` forward. It leaves `new Date(<value>)`, `Date.parse`, `Date.UTC`, the prototype (`instanceof`, subclasses), timers and monotonic clocks (`performance.now()`, `process.hrtime`) unchanged. A test that assigns `Date.now = () => …` itself and then restores it runs as if there were no preload. `TRACY_TEST_CLOCK_OFFSET_DAYS` sets the shift: unset = 400 (longer than the 72-hour session TTL, the 7-day invitation TTL, and more than a year); `0` = a control run at real time; a value that is not a non-negative number makes the preload stop the process before it replaces `Date`.

**Run:**

```
pnpm test:clock-shift <file> [<file> …]            # the named files
pnpm test:clock-shift --changed-since <ref>        # test:workers files added/edited since the merge-base with <ref> (including staged, unstaged, not yet added)
pnpm test:clock-shift --all-workers                # the whole test:workers list (workersFiles() of check-tests.ts)
pnpm test:clock-shift --check-excluded             # is each excluded file still red under the shifted clock?
TRACY_TEST_CLOCK_OFFSET_DAYS=0 pnpm test:clock-shift <file>   # control run at real time
```

Exit 0 = no file red · 1 = some file red, or the run could not be prepared/completed (git error, missing ref, truncated diff, empty workers list, a test directory that could not be listed, log could not be written) · 2 = wrong command syntax or wrong shift.

**A file's verdict is the EXIT CODE of the child process, nothing else:**

- Each file is one process `node --import scripts/clock-shift.mjs --test --test-timeout=120000 --test-force-exit <file>` (exactly the flags of `test:workers`), at most 600 seconds. Exit 0 → `HOLDS`. Non-zero exit, death by signal, or timeout → `FAIL`. The runner does NOT read the test report: it does not count tests, compare test names, or judge whether the report is complete.
- The consequence, stated plainly: exit 0 says only what `node --test` says. A file that registers no test, and a suite that skips itself when PostgreSQL is missing, both exit 0 and have NOT been checked under the shifted clock. Each run's summary line repeats this (`a self-skipped test was NOT checked`); to know which tests were skipped, read the file's log.
- The child process's output is written verbatim to a separate log file for each test file, in a new directory under `TRACY_CLOCK_SHIFT_LOG_DIR` (unset = the system temp directory); the path is printed at the start of the run and on each verdict line. The log of a `FAIL` file is also printed verbatim right above the `FAIL` line (on a CI runner the reader cannot reach the file). A log that cannot be opened or closed → the run stops and is red.
- A red run ends with the hint "a credential minted at a fixed time is being verified against real time — mint it with the verifier’s clock or inject the same clock into both". That line is the COMMON cause, not proof: the file's own log decides. Do a control run with `TRACY_TEST_CLOCK_OFFSET_DAYS=0`: still red means it is an ordinary red test.
- A file that does not exist, a directory, symlink, FIFO, a file outside the repo: `FAIL … refused before running`, no process is opened for it.
- A child process that CANNOT start (spawn throws or emits `error`): `NOT RUN … could not start`, the command is red in every mode. That is not an exit code, so not a verdict on the file: `--check-excluded` does not count it as `STILL NEEDED`. If the preload trial before the run cannot start or is killed, the whole run stops with exit 1 (`the run stopped: the preload could not be tried`), not reported as a syntax error (exit 2).

**Exceptions by FILE (`EXCLUDED` in `run-clock-shift.mjs`).** The trial catches every clock-sensitive test, not only credentials. Measured 05/10/2026 on the dev machine, without PostgreSQL: 14 of 804 `test:workers` files green at real time and red when shifted, none because of a credential. 13 files compare the shifted `Date.now()` with a clock the preload cannot shift: file mtimes (`draining()`, write locks, old run directories), `date` in shell scripts, child processes (PHP, the EmDash adapter). The 14th file, `apps/tracy-web/test/brief-guard.test.mjs`, is a REAL calendar bug not yet fixed: `guard.js` accepts the current year ±1 while the test hard-codes 2025 and 2026, so that test will be genuinely red from 01/01/2027 (separate work, not fixed here). Rules for the list:

- Each entry is `{ file, reason }`: exactly ONE file path and a measured reason. No directories, no patterns, no duplicates, no other fields (no per-test exceptions). The runner refuses a malformed list before running anything.
- **An exception entry excludes the WHOLE file.** A file with an entry is NOT run under the shifted clock in any of the three ordinary modes (named files, `--changed-since`, `--all-workers`); it is printed as `EXCLUDED <file> — <reason>` and counted in the summary line.
- What is NOT checked, stated plainly: all 14 of those files. A credential minted at a fixed time that a PR adds to an excluded file is NOT seen by this trial. That is the price chosen so the verdict rests on the exit code alone; when you edit a file on the list, run the control yourself and read the log.
- Do not use the list to silence a clock-skewed credential or an infrastructure error. On a new `FAIL`: do a control run, read the log. Credential → fix the fixture per the convention above. A clock outside the preload's reach → add an entry with its reason, in the same PR.
- `--check-excluded` runs each excluded file ONCE under the shifted clock and looks only at the exit code: non-zero (including signal, timeout) → `STILL NEEDED`; 0 → `NO LONGER NEEDED` and the command exits non-zero so the entry gets removed; a child process that cannot start → `NOT RUN`, the command is red too. An excluded file that no longer exists → `FAIL … refused before running`, the command is red too. `STILL NEEDED` only proves the file still exits non-zero under the shifted clock, NOT that the cause is still the recorded reason: to know that, read the log.

**Where it runs:**

- *Locally:* by name, as above.
- *PR (`Tracy CI`):* a STEP of the `tests related` row (ordinary PRs into `develop`) or `tests 2/2` (PRs into `staging`/`main`), after the `Build check` step: `node scripts/run-clock-shift.mjs --changed-since HEAD^1`, i.e. only the `test:workers` files the PR adds or edits (the `build-check` checkout takes `fetch-depth: 2` to have HEAD^1; a missing HEAD^1 turns the step red, it does not quietly run 0 files). The list comes from `git diff --diff-filter=d`: every status except deletion, so a type change (symlink ↔ regular file, status `T`) is selected too; a test file turned into a symlink is selected and then refused (`refused before running: is a symbolic link`), the step is red. A rename counts as delete + add; deleted files are not run; a PR touching no test file makes the step print `0 file(s) to run` and stay green. No added job, no re-run of the whole suite on a PR, not part of `check-all.ts`.
- *Nightly:* the same step runs `--check-excluded` and then `--all-workers` (concurrent processes = core count minus one, like `node --test`). BOTH commands always run: an exception entry no longer needed turns the step red but does not block the full run; the step is red when either is red.
- The step sets `TRACY_CLOCK_SHIFT_LOG_DIR` to `runner.temp` (the runner cleans it after each job).

### Rebuilding bundles after a merge — `pnpm bundles:regen`

`lib/client.js` and `lib/index.js` are still committed (RULE #3) and the `bundles` gate is unchanged. What was added on 04/10/2026 is **a local fix-up command**, not a new gate: after the source has been merged, it finds exactly the bundles that are stale, rebuilds them with that package's own `build` command, then runs the `bundles` gate as is. No merge driver, no CI job pushing commits by itself.

**Why it is needed.** When two branches both rebuild one bundle, the conflict is in a minified file nobody can merge by hand. Choosing "ours" or "theirs" yields a bundle missing the other branch's source changes; rebuilding only the package you remember misses other packages that embed the same shared source (`@tracy/core` is in many bundles). Neither reports an error locally.

**Order of work:**

1. Merge the target branch (`git merge origin/develop`). If the `vendor/tracy/deepseek-harness` pointer or the lockfile changed with the merge: `git submodule update`, `pnpm dsh:build`, `pnpm install` first — the builder reads `node_modules`, and an old dependency tree yields a bundle different from CI's.
2. **Resolve SOURCE conflicts first** and `git add` each source file. Conflicts in `lib/client.js`, `lib/index.js` (and `tracy-brand`'s `src/client/generated.ts`) are **left as they are** — no hand edits, no `git checkout --ours/--theirs`.
3. Run the command; the log directory must already exist and lie OUTSIDE the worktree:

   ```
   mkdir -p /tmp/tch-bundles && pnpm bundles:regen --artifacts /tmp/tch-bundles
   ```

4. When the command exits 0, read the list of files it prints and **`git add` them yourself** — the command never stages or commits. Then commit the merge as usual.

**What the command does.** Runs `--check` of EVERY builder under `packages/` (including packages the merge did not touch); for `tracy-brand` it also runs `gen-palette.mjs` on a copy of the inputs to learn whether the palette is stale; runs `pnpm run build` once for each package with a stale build; checks every builder again; compares the tree with the starting state (only files already identified as stale may change bytes); finally runs `pnpm exec tsx scripts/check-all.ts --only bundles`.

**The command refuses (exit 1, naming the file) when:** Git still reports unresolved conflicts (`git diff --name-only --diff-filter=U`) in a file that is not a known build output; a package's `build` is not one of the three command shapes in use, or a package has an unknown `build-*`/`gen-*` script; `--check` fails for a reason other than "stale bundle" (a name missing from `inject`, an esbuild error, a missing dependency) — it must exit 1 and its whole stderr must be exactly one of the builder's stale/missing messages; a build fails or times out; a build finishes and is still stale; a file outside the list of stale builds changed; the `bundles` gate is red. Wrong arguments exit 2.

**The command is not a security fence.** It trusts the tree it runs in: it only asks Git about conflicts (a source file already `git add`-ed that still holds `<<<<<<<` markers is the conflict resolver's problem), does not inspect symlinks or special files, does not stop other processes from editing the tree while it runs. The `bundles` gate on CI is still where the committed result is judged.

**When the command refuses.** It restores nothing: the tree stays as it is, the changed files are listed, each child process's log and `summary.json` are in `regenerate-bundles-*` under the `--artifacts` directory. Fix exactly the cause named and run again — running again is safe, a second run on an already clean tree builds nothing.

- ⚠ **On a clean tree of the target branch, the command must report "nothing stale".** If it wants to rebuild a package you did not touch, the machine's dependency tree differs from CI's; redo step 1 and **do not commit** those bundles.
- **Scope checked:** the command's behaviour is tested on a temporary Git repo (`scripts/test/regenerate-bundles.test.mjs`). The repo's real `bundles` gate is run by CI; the command only calls it and passes its result back.
- **Savings not yet measured.** After use, record for measurement: the number of bundle conflicts, the time from conflict to a green `bundles` gate (`elapsedMs` in `summary.json` is only the time of one command run), the number of rebuild runs per occurrence (each run is one `regenerate-bundles-*` directory), and the number of times CI was still red on `bundles` because of a stale bundle.

| `ci:e2e` | the `tests e2e` row **always runs** (the path filter does not overrule someone who asked); the three `tests emdash-*` rows run **by path** as before (a PR not touching a theme still has none) | the `tests e2e` row and the three `tests emdash-*` rows **do not exist** in the run |
| `ci:integration` | the `test:workers` test files that read `TEST_DATABASE_URL` **stay** in the run (as before) | those files are **left out** of the workers test part; unit tests in the same shard still run |

- 🔒 **The three EmDash rows are browser rows too (18/10/2026).** Each theme suite has `tests/visual.test.mjs` (all three), `audit.test.mjs` and `qa.test.mjs` (all three, via `tools/audit.mjs` and `qa.mjs --browser`) that open a real Chromium, and `check-tests.ts` calls `ensureBrowser` for all three rows. No list or flag separates the browser part from the rest of the suite (a theme's `pnpm test` is `node --test tests/*.test.mjs`), so without the label the **whole row is dropped**, like the e2e row; a dropped row is recorded in `leftOut` (notice `SKIPPED tests emdash-… add the label ci:e2e`, a step-summary block, `tested scope` = `partial:…e2e`). The merge gate (`check-pr-merge.mjs`) and `ci-label-rerun.yml` **need no change**: they read the `ci:e2e` label and `tested scope`, not row names; adding `ci:e2e` re-runs and the EmDash rows reappear.
- 🔒 **The two browser tests of `tracy-design-inspiration` now live in `test/e2e/`** (`template-body.test.mjs`, `template-body-loading.test.mjs`; the fixture `template-body-page.mjs` stays in `test/fixtures/`): they used to open Chromium inside `test:workers`, so an ordinary unlabelled PR still started a browser. The `tests e2e` row now owns them (the e2e owner is derived from the path, no hand-kept list). Goal: a PR into `develop` without `ci:e2e` opens no browser anywhere in Tracy CI.
- 🔒 **Unchanged, with or without labels:** PRs into `staging`/`main` (release), the nightly `schedule`, `workflow_dispatch`, push. They run every row and every test as before. A label on a release PR has no effect, and the re-run workflow does not listen to labels on PRs not targeting `develop`.
- 🔒 **Fail closed:** labels cannot be read (API error, missing permission, an answer that is not this PR, the PR changed its base branch, ≥ 100 labels), the diff cannot be read, or the diff is empty → **nothing is left out**, everything runs as before, with a `::warning::`. The `Read this pull request's labels` step of the `plan` job writes **no output** when the read fails; `plan-ci.mjs` reads an empty output as "unknown".
- 🔒 **Labels are read at run time through the API (`GET /pulls/{n}` with `GITHUB_TOKEN`; the `plan` job also has `pull-requests: read`), not from the event payload.** A re-run replays the old payload — labels added later are not in it.
- 🔒 **A PR that edits a database test itself leaves nothing out.** If the diff touches a file under `test/` or `tests/` containing `TEST_DATABASE_URL` (a `*.test.mjs` file or a helper such as `_db.mjs`), `plan` keeps the database tests (no label needed): the file the author just edited must run. Why this blunt rule instead of "run exactly that file": a second file-selection mechanism would have to pass through the Turbo hash, the tracer and `check-tests.ts`, and a mistake there would make the just-edited test silently not run. The finer option (run only the edited file) is kept for if such PRs become frequent enough to be worth it.
- **What "gated" means.** Exactly the classification `check-tests.ts` already uses to know whether a run needs a database (`ensureDatabase`): a test file whose contents include the text `TEST_DATABASE_URL`. One single definition, `isDatabaseGated` in `scripts/ci/related-tests.mjs` (planner, gate and Turbo all import it). Measured 16/10/2026 (recounted after the planner's two tests built the string from a constant): 1388 `test:workers` files, **148 gated files**: 140 in `apps/tracy-web` (real database tests) and **8 in `scripts/test/`** (`check-prepush-postgres`, `check-push`, `content-api-joomla-runtime`, `new-test-proof`, `regression-script`, `related-tests-gate`, `run-clock-shift`, `test-trust`). ⚠ Those eight are tests of **CI/hook tooling** that name the variable in a string or in a fake env and need no database — they are left out along with the rest, because the classification is a substring match (on purpose: better to wrongly leave out a tooling test than to run a database test without a database). They run again in the nightly, release PRs and with `ci:integration`; a PR editing them is not left out (rule above). 🔒 **The planner's own tests must not count as "gated"**: a test file naming the variable would be left out of every PR editing `plan-ci.mjs`, `test-scope.mjs`, `related-tests.mjs`… without the label — i.e. the planner's own tests would silently not run when it changes. So `ci-plan.test.mjs` and `ci-test-scope.test.mjs` build the variable name from the constant `DATABASE_MARK`, and `ci-test-scope.test.mjs` asserts that no `scripts/test/ci-*.test.mjs` file is classified as gated (the figure 148 above excludes them). To keep them in the default run, narrow `isDatabaseGated` to "reads `process.env.TEST_DATABASE_URL`" (removes 5 of the 8 files; the other 3 have the text in a fixture) — one line, but the owner's decision.
- **Where it applies.** `plan-ci.mjs` (`planMatrix({ labels })`, a pure function; the decision is in `testScope` in `scripts/ci/test-scope.mjs`) drops the e2e row, filters the `tests related` row, and sets `TRACY_TESTS_SKIP_DB=1` for the row's test steps; `check-tests.ts` enforces it (`--skip-db-gated` or the variable). The `tests related` selector removes gated files from the list; if it removes all of them (and there is no interop) there is **no** `tests related` **row**, as with a docs-only PR. Turbo rows: the same rule, and usable because the env is part of the hash (below).
- **Reported, never silent.** (1) `plan`: `::notice::SKIPPED tests e2e …` and `::notice::SKIPPED database tests: N workers test file(s) … add the label ci:integration`, plus a block in the step summary; (2) each row leaving files out: `check-tests: N workers test file(s) … were left out …`, the list of every file, `::notice title=database tests skipped::` and a block in the row's step summary. A row needs no database provisioning (no `docker`, no temporary container) unless it runs the e2e part or the whole gate (no `--part`).
- **Local commands.** `pnpm exec tsx scripts/check-tests.ts --part workers --skip-db-gated` or `TRACY_TESTS_SKIP_DB=1 pnpm exec tsx scripts/check-tests.ts --part related`. The variable accepts only `1`, `0` or unset; any other value (`true`, `yes`…) is an error, not a guess. The flag and `--database owned` are mutually exclusive. The gate **reads and then deletes** the variable from its own environment, so no test process inherits it (the interop tests spawn this gate again and would assert on a mode they did not ask for). The sharded gate picks the shard **first** and leaves files out **after**: a file belongs to the same shard with or without the skip. A shard emptied by the skip is **red** (a shard that tests nothing is red, as before).

**"Already green" must account for the flag — in two places.**

1. **Turbo cache.** The variable `TRACY_TESTS_SKIP_DB` is in the `env` (that is, in the hash) of every owner task that has gated files: `test:ci:1..3` of `apps/tracy-web` and `//#test:ci:scripts` (generated by `turbo-setup.mjs`, `groupDefinitions`; the `turbo-config` gate is red if an owner with gated files has a task lacking the variable — `configProblems`). A run that skips the database and a run that runs it are **two different cache keys**, so a green result of one is never returned for the other. `plan`'s hash-probing step, the steps `Compare every Turbo task hash`, `Turbo tests` and `Build check` set the variable at **step level** (`1` or `0`, never blank), not at job level: the clock-shift re-run step runs test files and must not inherit it. Tasks without gated files (every other package, `interop`, `vendor`) do not hash the variable, so adding `ci:integration` re-runs **only** the tasks whose result can change. Measured 16/10/2026 on the real configuration (`turbo run … --dry=json`, 47 tasks): unset, `0` and `1` give three different hashes in exactly 4 tasks (`@tracy/web#test:ci:1..3`, `//#test:ci:scripts`), the other 43 tasks unchanged; hence the workflow always sets `1` or `0`, and after the merge those four tasks miss the cache exactly once (`ci-turbo-hashes.test.mjs` keeps this measurement). `plan`'s `--scope` step decides before asking Turbo; `Plan the rows` decides again from the same labels and is **red** if the two answers differ. Regenerating the configuration: `turbo-setup.mjs` (no flags) refuses to run while the variable is on — the measurement must see the database files too.
2. **`green_run` (a tree already green does not re-run the full suite).** A PR into `develop` keeps all seven release row names when the planner falls back to "run every row" but still leaves out the database tests; looking only at row names would mistake it for proof of "fully green" for a release PR on the same tree. Now every run also writes a `tested scope` annotation (`full`, or `partial:db`, `partial:e2e`, `partial:db+e2e`) next to `tested tree`, and `proofProblem` accepts only a run that wrote **exactly `full`**. A run that wrote none (every run before this change) is **not** proof — the same cost as the `tested tree` record: the benefit starts from the next run. `check-pr-merge.mjs` checks the same condition again.

**Re-run on labelling — the `ci-label-rerun.yml` workflow.** Trigger **`pull_request_target`** `types: [labeled]`, branch `develop`; the job runs only when the label is `ci:e2e` or `ci:integration`, the PR is not a draft and the source branch is in this repo; permissions `contents: read`, `actions: write`, `pull-requests: read`; runner `tracy-light` in the right lane. `scripts/ci/label-rerun.mjs`: reads the PR **at that moment** (still open, the current branch head), finds the newest `tracy-ci.yml` run of the `pull_request` event for that exact `head_sha` and this exact PR — "newest" by when the last attempt **started** (`run_started_at`, using the same `newestRun` as `check-pr-merge.mjs`), not by run number; **if it is running, cancels it and waits until `completed`** (at most 10 minutes), looks at the branch head once more, then `POST /rerun` the whole run (not `rerun-failed-jobs`: `plan` must decide again). No run for that branch head → does nothing (the run that starts will read the labels itself); the branch head changed while waiting → the old run is not re-run. Removing a label does nothing. The API refuses → the job is **red** with the answer. The step summary records which run was re-run.
- 🔒 **Why `pull_request_target`, and why it is safe here.** The job holds `actions: write` on a self-hosted runner, so it must not run the PR's code. With ordinary `pull_request`, `actions/checkout` takes the merge commit and `label-rerun.mjs` (along with the workflow file itself) written by the PR's author would run with that token. `pull_request_target` runs the workflow file of the **base** branch, and the job checks out only `github.event.pull_request.base.sha` with `persist-credentials: false`: nothing from the PR is executed, no credential remains in the checkout (same convention as `auto-merge-develop.yml`). What is taken from the event is only data — the label name (one of the two, filtered by `if`) and the PR number — passed through env, not into a command; the PR's branch head is read again from the API on the spot and the script only calls this repo's REST API. ⚠ Until the file is on `develop` there is no `label-rerun.mjs` at the base commit: the first label after merge is the first run.
- 🔒 **The `concurrency` group is split by label.** The group is computed **before** the job's `if`, so every `labeled` event (triage, area…) creates a run in the same group; if the whole PR used one group with `cancel-in-progress`, an unrelated label added right after `ci:e2e` would cancel the job that is cancelling-then-re-running Tracy CI, and nobody would re-run it. Now the two watched labels share one group per PR (the later label cancels the earlier job and does the whole work), every other label has its own group `github.run_id`. The test `ci-label-rerun.test.mjs` evaluates the group expression for an unknown label.
- 🔒 **The two labels must exist in the repo.** `ci:e2e` and `ci:integration` **have not been created** (this change creates no labels): whoever opens a PR runs `gh label create ci:e2e` and `gh label create ci:integration` once before use — without the labels nobody can add them and PRs into `develop` still leave out the two test sets.
- 🔒 **Why `labeled` was not added to `tracy-ci.yml`.** Its `concurrency` groups by ref with `cancel-in-progress` for PRs: any label (triage, area…) would cancel the running run, and a `labeled` run that `plan` skips ends `skipped`, which can overwrite the required check of the head commit with "skipped".
- ⚠ **Not verifiable here (needs a real label):** whether `GITHUB_TOKEN` may call `POST /actions/runs/{id}/rerun` on this repo. The tests run against a fake API. If it is refused, the job is red with GitHub's answer; the fallback without a design change: take the CI App's token (`actions/create-github-app-token`, `permission-actions: write`) the way `plan` already takes a read token.
- 🔒 **The merge gate knows the labels.** `check-pr-merge.mjs` (and the `Auto Merge Develop` bot, which runs that same command) for a PR into `develop`: reads the PR's labels and compares them with the `tested scope` the newest Tracy CI run wrote. `ci:integration` present but the run left out database tests (`partial:db…`) → **FAIL**; `ci:e2e` present but the run dropped the e2e row → **FAIL**; a label present but the run wrote no scope → FAIL; the message says plainly "wait for the re-run that adding the label starts". Reason: between adding the label and `/rerun` resetting the check, the old green run is still the newest (and stays so for good if `/rerun` is refused). A run that skipped the whole suite thanks to `full` proof is not questioned. An open release PR with old proof (no `tested scope`) will FAIL this gate until it is re-run.
- ⚠ **The `Auto Merge Develop` bot merges a PR as soon as it is green on the exact head.** To get E2E/database tests before merging, **add the label while the PR is still a draft** (the run started by pressing Ready reads the labels itself) or right after pressing Ready (CI re-runs by itself); a label added after the PR is merged leaves nothing to re-run.

**`new-test proof` and `tests related`.** (1) `new-test proof` is **unchanged**: it already removes `TEST_DATABASE_URL` from the test environment and builds no database, so a test file needing a database is always `not-runnable` there, label or not; there is nothing to switch on. (2) `tests related`: a test file **edited by the PR itself** still runs even if it needs a database — through the rule "a PR editing a database test leaves nothing out" above (the other database tests run along with it; accepted to avoid a second selection mechanism). A PR that edits no database test but edits code a database test reads: those tests do **not** run on the PR (that is what David chose); they run in the nightly, release PRs and with the label.

**Noted, not fixed.** (1) A PR created with a label fires `opened` and `labeled` at once: the first run is cancelled and re-run, costing one run (labelling while still a draft avoids it). (2) There is a millisecond-scale window between the last look at the branch head and `POST /rerun`; a branch head pushed exactly then makes the old run re-run, and the new run reads the labels itself. (3) Hash coverage of the database files is only measured in the nightly and release PRs (a run with the skip only measures the subset of files it runs; `turbo-setup.mjs` refuses to regenerate the configuration while the variable is on).

**Not yet measured.** The runner-time saving is not measured (needs a few days of real runs). The eight tooling files left out along the way (above) and whether `GITHUB_TOKEN` can re-run have not been checked on GitHub.

### PostgreSQL for `test:workers` locally and in pre-push (since 05/10/2026)

**The gap.** A bare `pnpm test:workers` provisions no database: files under `apps/tracy-web/test/` that start with `skip: set TEST_DATABASE_URL` print "skipped", node exits 0, and the hook reports green for tests that never ran. `scripts/check-tests.ts` is the existing wrapper built to stop exactly that (it finds a database itself, and with none it is **red**), but the hook called the bare command, not the wrapper.

**Local commands** — the same test suite, with a database:

```
pnpm exec tsx scripts/check-tests.ts --part workers                    # database sources in the old order
pnpm exec tsx scripts/check-tests.ts --part workers --database owned   # only the run's own database
TRACY_PRE_PUSH_POSTGRES=1 git push                                     # the hook uses the second command instead of pnpm test:workers
```

| | No flag (as in CI and `pnpm build:check`) | `--database owned` |
|---|---|---|
| `TEST_DATABASE_URL` exported | used if it answers; **no answer → red**, no fall-through to the next source | not read, not probed |
| `deploy/.env` | used if it answers | file not opened |
| Temporary container `postgres:16-alpine`, port `127.0.0.1:55432` | last source | only source |
| No usable source | red | red |

- **A borrowed database is never touched.** The first two sources belong to someone else: the gate only reads them, never starts, stops or deletes them. The only thing the gate deletes is the container it created itself, by the **64-hex-character id** that `docker create` returns (`docker rm -f -v <id>`), never by name. If `create` prints anything other than a full id → treated as not created, nothing started, nothing deleted.
- **`owned` forgets the inherited URL before doing anything else.** The pushing shell's `TEST_DATABASE_URL` is removed from the test suite's environment at the very start, and only written back with the URL of the container that just answered `select 1`. If the private database does not come up → the gate is red and the suite does not run; it does not fall back to the inherited URL.
- **A wrong flag is red, not "pick something".** The gate reads **all** arguments: each word must be `--part` or `--database` with exactly one value. A mistyped flag name (`--databas owned`, `-database`, `--db`), an extra word, a missing value, a repeated flag, `--database=owned`, or a value other than `owned` → exit 1 before any database work. Before 05/10/2026 a mistyped flag name was ignored and the run silently became "no flag", i.e. borrowed the inherited database.
- **Why the hook uses `owned`.** The hook runs in the pusher's shell; `TEST_DATABASE_URL` there may be another session's stand or a customer database. The test suite creates and drops schemas, so the hook must not borrow something it does not know the owner of. **Never point `TEST_DATABASE_URL` at a customer database or a shared dev cluster** — on the no-flag path, the gate trusts that variable.
- **The hook never hands the shell's `TEST_DATABASE_URL` to the test suite, on either path.** The default path removes that variable before calling `pnpm test:workers` (without removing it, "no database" would become "run on whichever session's database exported the variable"); the `=1` path removes it and only takes back the URL of the container it just built. ⚠ The removal exists only in the hook: `pnpm test:workers` **typed by hand** still reads the typing shell's variable — if it is exported, tests needing PostgreSQL run on that very database.

**`TRACY_PRE_PUSH_POSTGRES`.** Unset, empty or `0` → `pnpm test:workers`, no database. Exactly `1` → the `--database owned` command runs **instead of** the bare command (not both). Any other value (`true`, `yes`, `01`, with spaces…) → the hook **blocks the push** and runs no test: guessing "on" would build a container nobody asked for, guessing "off" would run fewer tests than the pusher thinks. The variable is read only when the push qualifies for running tests (branch `main`/`develop`, a base exists, touches `apps/`·`scripts/`·`packages/`). The chosen command being red — including because the database could not be built — blocks the push.

**Why it is optional, not the default — measurements.** The condition set before wiring it in: put the database run on the blocking path only once a real PostgreSQL run succeeds and the added time is at most 60 seconds. Measured 05/10/2026 on the shared dev machine (macOS, Docker 29.7.2), four runs, each running the bare command and then the `--part workers` wrapper:

| Run | `pnpm test:workers` | With PostgreSQL (build + suite + delete) | Added |
|---|---|---|---|
| 1 | 218.4 s | 280.4 s (1.6 + 278.2 + 0.6) | 62.0 s |
| 2 | 204.4 s | 277.8 s (1.4 + 275.8 + 0.6) | 73.4 s |
| 3 | 232.8 s | 470.7 s (1.5 + 468.3 + 1.0) | 237.9 s |
| 4 (final check run) | 331.2 s | 383.5 s (2.1 + 380.7 + 0.7) | 52.3 s |

- Three of the four runs exceeded 60 seconds; run 4 was below the threshold (52.3 seconds) → still **optional**, for two reasons. One: **no run, including run 4, went through the `--database owned` path** — all four used a database the measurement created on another port (see the ⚠ line below), so the condition "a real PostgreSQL run succeeds on the path that will be wired into the hook" is not met. Two: the spread between runs (52–238 seconds; run 3 ran while the machine was busy with another session's work) shows that one run under the threshold is not yet a stable added cost. The bare command by itself already takes 204–331 seconds, no longer the "seven seconds" it took when the hook was written.
- Skipped tests (run 2, both commands exit 0): the bare command 14,603 tests, **1,112 skipped, of which 1,084 for lack of `TEST_DATABASE_URL`**; with a database 14,695 tests, 4 skipped, **0 for the database**. Run 4 gives the same skip counts (bare 14,562 tests, 1,112 skipped, 1,084 for the database; with a database 14,694 tests, 4 skipped, 0 for the database; both exit 0). So each default push reports green for 1,084 tests that never ran; Tracy CI runs them, but only on pull requests.
- Run 1 was measured with `NODE_OPTIONS=--test-reporter=tap` and both commands were red on exactly 5 tests of `scripts/test/clock-shift.test.mjs`: that variable leaked into the node processes the test spawns itself. That is a fault of the measurement, not of the suite (run without the variable: exit 0); runs 2, 3 and 4 dropped the variable and both commands were green. Run 1's times are still recorded because they point the same way.
- ⚠ **The `--database owned` path has not been fully measured with a healthy database.** On the measurement day, port 55432 was held for two days by a `tch-check-tests-postgres-…` container from another run (a sign of a run hit by `kill -9`, see the limits below). The wrapper behaved correctly: `docker start` reported `port is already allocated`, the gate deleted **its own** container and exited 1, the other container stayed intact. The measurement runs therefore used a PostgreSQL the measurement itself created on another port and handed to the wrapper through `TEST_DATABASE_URL` — same image, same suite, same wrapper; only the container-building stage differs.

**Remaining risks.**
- **One fixed port.** Two `owned` runs at once on one machine: the later run is red (it does not delete the earlier run's container). A container left behind holding the port makes every `owned` run red until **its owner** deletes it by id.
- **`kill -9` or out-of-memory** midway cannot clean up (a limit already written in `check-tests.ts`); Ctrl-C and SIGTERM still clean up.
- **Not checked:** the real hook called by prek in a real `git push` (the tests use a copy of the hook in a temporary repo, with fake `pnpm` and `docker` on `PATH`); the "database answers" branch of `--database owned` with real Docker; and everything only a GitHub Actions run shows — Tracy CI does not use this flag and is unchanged.

### Self-skipped tests and the shard table — measurements taken from the runners (since 08/10/2026, #1028)

**The gap.** The CI run of PR #1021 (run 37707424087): `tests 1/2` ran 655 s of workers, `tests 2/2` ran 969 s of workers plus 197 s of `rest` (interop + dsh-passwords). `scripts/test-timings.json` had 494 of the 866 existing workers files (372 files missing, weighted by the median; 4 entries pointing at deleted files) and its numbers were measured on a Mac on 29/09. A table re-measured on macOS was reverted (`7cdbcfb46`): it split the runners into 225 s / 457 s, while the hand-typed table gave 358 s / 352 s. Measurements on a dev machine say nothing about the runner.

**Old logs have no per-file duration — read, not guessed.** The `spec` reporter of `node --test` prints each TEST's duration and does not print the file name (read on run 37707424087: 9,577 lines of `tests 1/2`, none carrying a file duration). Summing test durations does not give a file's cost: it omits process start-up, imports and `before()`, exactly the part that makes a file heavy (run 36596428799). So **the table was NOT refilled in this PR**: no real numbers, no typed numbers.

**What was added: each shard prints its own measurements.** `scripts/test-timing-reporter.mjs` is a second reporter, running BESIDE the ordinary one (`--test-reporter=spec` prints exactly as before; the exit code is the runner's):

| Log line | Printed by | Meaning |
|---|---|---|
| `tracy-test-timing v1 begin part=workers shard=i/n files=N` | `check-tests.ts` | opens a shard, N files assigned |
| `tracy-test-timing v1 file=<path> seconds=S ok=1\|0` | reporter | the child process of ONE file, from start-up to exit. Only the runner's file-level record (`test:complete`, nesting 0, line 1 column 1, name = the path passed in) counts; a test's duration is never a file's duration |
| `tracy-test-timing v1 conflict file=… reason=…` | reporter | the file has two records, no usable duration, or a path with whitespace: no number for that file |
| `tracy-test-timing v1 files=N summed=S` | reporter | the number of files with a measurement and their sum |
| `tracy-test-timing v1 end part=workers shard=i/n wall=W` | `check-tests.ts` | printed only when the shard is green; W is the shard's wall time |
| `tracy-test-timing v1 part=rest wall=W` | `check-tests.ts` | wall time of `rest` on the last shard |

- ⚠ **The report block is written synchronously, because the gate runs `--test-force-exit`.** Measured on node 24.15: a force-exited run does not receive the overall `test:summary` event, prints nothing after the event stream closes, and a 600-file block written through a pipe via the reporter's stream was lost entirely (0/600 lines; written to a file, all 600 arrived). The reporter therefore writes the whole block in one synchronous call to the file `spawnReported()` names, right when it receives the runner's last `duration_ms` line; the parent process prints that block again with `printNow()` (synchronous write, waiting when the pipe is full). Tried 5 runs through a pipe with 600 files: all 600 lines all 5 times.
- Each report block ends with the line `check-tests: end of the skip/timing report`. A run that leaves no report, or leaves an empty or truncated file (last line not that end line), makes the gate print the part of the file it has and then `this run left NO skip/timing report`: not red (the reporter decides nothing, the exit code is still the suite's), but the skip list is then not considered complete and that shard will be refused by the table importer.

**Filling the table: `scripts/update-test-timings.mjs`.** There is no local measurement mode any more.

```
node --import tsx scripts/update-test-timings.mjs [--runs N] [--repo owner/name]   # refill (default 5 runs, minimum 3)
node --import tsx scripts/update-test-timings.mjs --check-ci                       # check the committed table, writes nothing
node --import tsx scripts/ci/plan-ci.mjs --check-test-balance                      # predict the two tests jobs, no network needed
```

- **Which runs count:** `Tracy CI`, event `pull_request`, `completed/success`, exactly one PR targeting `develop`, both `build check (tests i/2)` jobs `success` on a runner labelled `linux`. Shard and `rest` timing lines are accepted only from the job with EXACTLY that name (whole-name comparison, `shardJobName()`); another job whose name merely ends in `(tests i/2)` is refused. The base branch is read from `GET /commits/{head_sha}/pulls`, not from the run's `pull_requests`: GitHub leaves that list empty once the PR is closed (read on run 37707424087 an hour after the PR merged). Each run counts once, by its latest attempt.
- 🔒 **Each sample is bound to exactly one repo, workflow file, PR, commit, run and attempt** (the same checks as `scripts/check-pr-merge.mjs`). A branch name is not enough: another PR (from a fork, or a later PR reusing the name) carries the same `head.ref`. The run and its head must belong to the repo being read and be a run of `.github/workflows/tracy-ci.yml`; the PR must have both head and base in that repo, `head.sha` equal to the run's commit, and there must be only ONE such PR (two PRs on the same branch, or a PR that received more commits after the run: refused); the run's `pull_requests`, when present, must name that PR; every job in the list must carry the run's `run_id`, `run_attempt`, `head_sha`. The PR number is written into `source.runs` and `--check-ci` compares it again.
- **Which shards count:** complete `begin`/`end`, complete summary line, number of file records equal to the number of files assigned, no duplicate records, no malformed lines, no red file, printed by the job carrying that shard number. Any one thing wrong refuses the whole shard with a reason: a shard missing lines looks exactly like a shard whose files ran fast.
- 🔒 **One single line shape.** Every log line containing the marker `tracy-test-timing v1` ANYWHERE must be a whole log line (`job<TAB>step<TAB>time content`) whose content starts with that marker and is one of the six records; a line with a truncated prefix, the marker inside the text of another line (including a test name quoting it), unknown content: the whole run is refused, naming the line. Consequence: a test that prints that marker to stdout makes every run refused until fixed (with a reason, not silently). A run with a `reporter error` or `left NO skip/timing report` line is not a sample either. A duration of `0.000` (file, shard, `rest`) is not a measurement and is refused like a missing one; the reporter itself writes `conflict … no-usable-duration` for a file under half a millisecond.
- **Values:** each file is the MEDIAN of at least 3 runs (`MIN_SAMPLES`), keeping three decimals as measured: no floor, small numbers are not rounded to 0 (`restWallSeconds` likewise); if any file has fewer than 3 samples the whole fill is refused and the table stays as it is. Entries for deleted files are dropped.
- **Two units.** A file's number is measured while many files run at once, so a shard's wall time = `wallPerSummedSecond` × the sum of its files' numbers (the median of `wall ÷ sum` over those same runs). `rest` is in wall seconds (`restWallSeconds`, the measured median; issue #1028 recorded 155 s for the run of PR #1025, run 37707424087 measured 197 s from the log timestamps); `shardOf` weighs by summed seconds, so `preloadLastShardSeconds = restWallSeconds ÷ wallPerSummedSecond`. A table that adds `rest` in the wrong unit is refused on read.
- **Writing the table:** a temporary file beside the table (created exclusively, flushed, read back and checked), then one `rename`. A lock file `test-timings.json.lock` refuses a second fill running at the same time (a run killed with `kill -9` leaves the lock behind: delete it by hand once sure that run is dead); a table replaced by someone else during the fill is refused. 🔒 There is no "check the name, then open" step: the table is opened with `O_NOFOLLOW | O_NONBLOCK` (a symlink is refused by the open call itself, a FIFO does not hang) and its type and size are read with `fstat` on the opened descriptor; directories, empty files and truncated JSON are refused from there. The table replacement is bound to the very file that was read: under the lock, the table is reopened and must have the same device, inode, size, modification/change times and the same bytes; the descriptor is kept open, and right before `rename` the name must still be that file, not yet written to. A name that became a symlink, another file or was written in place: refused, leaving whatever the other party left. Exactly one gap remains that POSIX `rename` cannot close: a writer NOT using the lock slipping in between the last look and `rename`.
- **Exit codes:** 0 done · 1 refused (reason on stderr, table intact) · 2 wrong arguments · 3 GitHub could not be read (network, authentication, timeout, empty log). Code 3 means NOTHING is known yet, not "the log has no measurements".
- **`--check-ci`** re-reads exactly the runs recorded in `source.runs` (id, attempt, commit, PR number), recomputes the table for the current tree and compares each value. A table not yet carrying `source.kind: "ci"`, a run that was re-run, a new file without enough samples, a number edited by hand: all exit 1.
- **`--check-test-balance`** uses the gate's own `workersFiles()` and `shardOf()`: exits 0 only when the table is a CI table, has every workers file, has no entries for deleted files, and the two predicted jobs differ by no more than 30 s (the last shard adds `restWallSeconds` exactly once, in wall seconds). ### Proving tests catch bugs — `scripts/test-trust.mjs` (since 12/10/2026)

**Why it exists.** The test suite was written almost entirely by agents, and nobody had measured which tests turn red when the code they guard is broken. Reading tests is not enough to conclude; this tool measures.

**What it does.** A cohort (`scripts/test-trust-<name>.json`) records a list of test files and mutants. A mutant is **one exact text replacement in one product file** (the same convention as `tests/qa/layers/api/red.mjs`: the `find` snippet must occur exactly once), with a `behaviour`: what a user or attacker could do if that bug reached production. The tool copies everything a run may load into a temporary tree under `--out`, keeping the repo layout; the worktree is only read, mutants only edit the copy. Each test file runs alone (`node --test --test-reporter=tap <file>`) through three stages: `control` (the untouched copy), each mutant, then `restored` (after the last mutant is removed).

**The temporary tree holds exactly the following, nothing more** (since 12/10/2026, cohort `auth`):

| What is copied | Taken from |
|---|---|
| the test file and every file it reaches through relative imports written as strings (including `.json`) | each file's syntax tree |
| targets of imports with a computed path | declared by the cohort in `computedImports` (file → a finite list of targets). A file with a computed import and no declared targets: refused, exit `2` |
| imported packages (`pg`, `hono`…) | the directory node finds from the importing file (the nearest `node_modules/<package>`, pnpm's link), then every package in its `dependencies`/`optionalDependencies`/`peerDependencies`, followed through the manifests. Links between packages are rebuilt **inside** the temporary tree; workspace packages go the same way. A package outside the repo or not installed: refused |
| files read with `fs` rather than imported (SQL migrations, locale tables, mail templates, contracts) | declared by the cohort in `assets`; a path ending in `/` is a whole directory |
| the `package.json` of every directory above those files | found automatically |

A file a run needs that none of the entries above names is **not in the temporary tree**: `control` is red with `ENOENT`/`ERR_MODULE_NOT_FOUND` and nothing is scored, instead of silently reading something unrecorded. The `--out` directory must lie outside the repo; the tool refuses when there is a `node_modules` above it (a run there could load unrecorded packages).

**Environment and database.** A run receives only `PATH`, `HOME`, `TMPDIR`, `SystemRoot`. When the cohort declares `"database": "postgres"`, the caller's `TEST_DATABASE_URL` is only the **server**: for each run (each file in `control`, each mutant cell, each file in `restored`) the tool creates a private database `trust_<pid>_<code>` on that server, passes that database's url, and drops the database when the run ends.

🔒 **Only one starting point is accepted, and it is CHECKED, not merely recorded:** the database is created from `template0` (`create database … template template0`) and **holds no objects other than PostgreSQL's own**. PostgreSQL assigns oids from 16384 upward to everything created after `initdb`; the tool counts those oids across 28 catalogs (`pg_class`, `pg_proc`, `pg_type`, `pg_policy`, `pg_rewrite`, `pg_extension`…), so a pre-existing table, view, policy or `schema_migration` ledger is caught without needing to know what kind it is. Non-zero is **refused**, not hashed into the receipt: a wrong starting point that is only hashed is equally wrong in `control`, every mutant and `restored` (the migrator skips SQL because the ledger already has rows) and `--verify` stays green.

🔒 **Tests also create databases themselves, and not from `template0`:** the helper `apps/tracy-web/test/_db.mjs` runs a bare `create database`, i.e. copies `template1`. The tool does not describe them as a second starting point: when probing the server, it creates one more database **exactly that way** (no template named) and refuses the server if that database does not start **identical** to the `template0` one — object count, every attribute of the `pg_database` row (encoding, collate, ctype, locale provider and rules, collation version, tablespace…, taken as the whole row so whatever columns the server version has are compared), and every setting a session may change. A `template1` with no objects but a different collation is therefore also a server that cannot be measured; the reason names the difference (e.g. `attributes/datcollate`). Thanks to this, a single state, `fresh`, stands for every database a run can meet.

The tool records the server version, the role's privileges, and `fresh`, read **inside the very database just created**, not the database the url points to: template, object count (always 0), `attributes` (the `pg_database` row minus name, oid and the two transaction counters), `settings` (encoding, collate, ctype, locale provider, time zone, `DateStyle`, `IntervalStyle`, `search_path`, `standard_conforming_strings`, transaction isolation level) and `session` (the count and hash of every setting the session may change). After each run, what that run left behind is recorded in `runs[].databaseAfter`: object count, a hash of definitions (relations with row security, columns and defaults, views, indexes, constraints, triggers, rules, policies, functions, types, extensions, schemas, sequences) and the list of migrations in the ledger. A state that cannot be read is **an error of the run**: an `inconclusive` cell for a mutant run, an invalid measurement as a whole for `control` or `restored`. A cohort with a database but no url, a server that does not answer, a role that cannot create databases, or either creation method not yielding an accepted starting point: **nothing runs**, the measurement is invalid with reason `inconclusive: the test database is not reachable`, exit `1`. A test that skips itself for lack of a database is never counted as passing (see the cell table).

```
node scripts/test-trust.mjs --cohort pilot --verify --out <results directory>
```

Each run creates a new directory `test-trust-<cohort>-<UTC time>-<code>` in `--out`, holding `result.json` (each run, exit status, timings, the matrix and `inputs`), `matrix.md` (a table to read) and `logs/` (TAP and stderr of each run). The temporary tree is deleted at the end.

**A result is bound to exactly the inputs measured.** Everything that decides a result is listed in **one single function**, `measuredInputs`, and written into `result.json` under the key `inputs`:

| Key | Content |
|---|---|
| `cohort` | name and sha256 of the cohort file |
| `runtime` | node version, platform, arch of the process running the tests |
| `tool` | sha256 of `scripts/test-trust.mjs`, every file it imports, and the `typescript` files node loaded (the tool reads imports with this parser's syntax tree) |
| `tests`, `sources` | sha256 of each test file and each file they load (relative imports and `computedImports` targets) |
| `assets` | sha256 of each file declared in `assets`; directories are expanded into files, so adding or removing a migration is a change |
| `manifests` | sha256 of the `package.json` in every directory above those files — node reads them to decide whether `.js` is ESM or CommonJS; these are also exactly the manifests copied into the temporary tree |
| `packages` | `resolved`: which file each (file, `import` or `require`, import name) lands on — the two styles read two different `exports` conditions, asked of node itself; `links`: where node found each package and each dependency (`absent` = declared, not installed); `files`: sha256 of **every byte** copied (a version number stands for no byte); `config`: sha256 of `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `.npmrc` when the cohort imports packages |
| `environment` | each variable passed to a run, as `sha256:<hash of the value>` or `unset`. No value (database password) is in the result |
| `database` | `null`, or the database kind, whether it is usable, the server version and role privileges the server reports, and `fresh`: which template a run's database is created from, how many objects it holds (0, checked), and which attributes and settings it carries. `reachable: true` also means a database created the test helper's way starts out identical. The schema after migration is a function of that empty starting point, the server version and the migration files in `assets`; all three are on this list |
| `mutants` | file and sha256 of each mutant's text replacement |
| `oracle` | the oracle's name; sha256 of `tests/qa/layers/unit/lib/sources.mjs`, every file it imports and the `typescript` files node loaded (taken from node's module cache, hashed by content, no version number used as a stand-in); and `mapping` — the test file → product file table the oracle returned. Each mutant's `guardedBy` comes from that table |

At the end of a run, that function is computed again: any entry that differs marks the measurement invalid. Later, to check whether an old result is still usable:

```
node scripts/test-trust.mjs --cohort pilot --check-receipt <the run's directory>
```

The command recomputes exactly that function on the current tree and runtime and compares **each entry** with the recorded `inputs`; an entry that differs, is missing or is extra is refused, printing the entry name (e.g. `input changed: manifests/apps/tracy-web/package.json`) and exit `1`. Exit `0` = the result still matches. A result recording an invalid measurement is refused too. Since recording and checking share one list, no input is used without being recorded, or recorded without being checked.

**One cell of the table (test file × mutant)** — the table always has one cell for every pair:

| Cell | Meaning |
|---|---|
| `killed` | a test green in `control` becomes `not ok` on the mutant with an **assertion** error (`ERR_ASSERTION`); the test's name is recorded |
| `covered-survived` | the test file is still green **and** that very run's V8 coverage shows the mutated snippet was executed |
| `not-covered` | the test file is still green and coverage shows the mutated snippet did not run. A static import is not proof of execution: the field `imported` records separately whether the file is in the import graph |
| `unknown` | the test file is still green but the run's coverage could not be read: reach **not measured**, not guessed |
| `equivalent-reviewed` | `covered-survived` **and** the cohort carries a handwritten argument (`equivalent.argument`) that the mutant cannot change behaviour. Without an argument it is never equivalent |
| `inconclusive` | everything else: code could not be loaded, timeout, death by signal, incomplete TAP, a test set differing from `control`, a new skip/todo, a non-assertion error, **or that file's `control` has a skipped test** (missing database, missing tool) — then every cell of the file is `inconclusive`, even when another test of the file is red on an assertion: counting that cell as `killed` would let `--verify` accept a file whose database tests never ran. **Never counted as a kill or a pass.** |
| `not-measured` | the run did not happen: the mutant could not be applied, the budget ran out, or the measurement was already invalid; the reason is in the cell |

Coverage is taken with `NODE_V8_COVERAGE` on each mutant run: the innermost block containing the first changed character decides, and any process of the run executing it counts. Two test files with the same kill set are only named **duplicate candidates** (`duplicateCandidates`), nothing more.

**`--verify` is red when** `control` or `restored` is not green or they differ in test names and pass/skip/todo counts; a mutant cannot be applied; there is an `inconclusive` or `not-measured` cell; an `expect.killedBy` of the cohort does not become `killed`, or the unit-layer oracle (`productSourcesOf` in `tests/qa/layers/unit/lib/sources.mjs`) does not link that test file to the mutated file; an entry of `inputs` (a worktree file, the oracle, the tool…) changes during the run; or **runner time** (`wallMs`: everything the tool does from start-up — hashing inputs, asking the oracle, creating / reading / dropping databases, the test processes — not just test-process time) exceeds the cohort's `budgetSeconds`. The budget also stops the runs themselves, in all three stages: no run (`control`, mutant, `restored`) starts once runner time has reached the budget, and each run is cut at the remainder; the remainder always deducts first the time to re-read the inputs at the end (measured on the first read). For mutants it also deducts the cost of the `restored` stage (measured in `control`, including creating and dropping the database): when it runs out, the cell is `not-measured`. `control` or `restored` not running for lack of budget makes the whole measurement invalid (the copy has not been proven restored). The maximum overrun is the time to kill a hung process (2 seconds). A file's `control` and `restored` leaving the database in two different states also makes `--verify` red. A `covered-survived` or `not-covered` cell does **not** make `--verify` red: it is a measured result to hand over, not a broken measurement. Exit `0` = measured (and passing with `--verify`), `1` = invalid measurement or verify red, `2` = wrong arguments or cohort.

### A tree already green does not re-run the full suite — `scripts/ci/green-tree.mjs` (since 10/10/2026)

Lee decided 10/10/2026: a `staging` → `main` release PR carries **exactly the tree** that was green on the `develop` → `staging` PR a few minutes earlier (#1136 and #1130 share tree `c24f1e478a…`), so re-running ~25 minutes of tests adds no information. Same tree = same bytes = same verdict.

- **Decided by tree, not by commit.** The `plan` job takes `git rev-parse HEAD^{tree}` of what it checked out — for a PR, the merge commit GitHub builds, i.e. exactly what the test suite will run. One byte different (a hotfix on `staging`, a base that moved on) is another tree → the full run as before.
- 🔒 **Every Tracy CI run records the tree it tested** with a `notice` annotation titled `tested tree` in the `plan` job (every event, including the nightly). This is the only record of what a `pull_request` run actually tested (the merge commit, not the head). Runs **before** this change have no record → not proof (measured 10/10: run 38069623159 of #1130 was rejected for exactly this reason); the benefit starts from the next release.
- **Proof must be complete** (`proofProblem`): a `tracy-ci.yml` run of `TracyHQ/tch` itself (repo and head repo — no runs from forks); `completed`/`success`; the latest attempt has **every row** `build check` of a full row set (`fullRowSets()` of `plan-ci.mjs`, no hand-kept list: the two-shard set, or since 17/10/2026 the forced five-row Turbo set — the latter counts ONLY when that run's `plan` job printed the notice `full run` = `turbo`, because PRs into `develop` have rows of the same names whose tasks may come from cache) and every row `success`; the tree it recorded as `tested tree` equals our tree. The head commit's tree (`head_commit.tree_id` in the run list) is only used to nominate candidates, not to decide. A cancelled/red/running run, an ordinary PR run with only `tests related`, a run with a skipped row, and a run that itself skipped (no rows at all) all do not count → skips cannot chain.
- **With proof** (only the `pull_request` event, into `develop`/`staging`/`main`): `plan`'s `green_run` output is non-empty → every `build-check` row is skipped by `if`; a job `full suite skipped: tree <hash> already green in run <url>` runs for a few seconds on `tracy-light` so the PR's check list and `/ops/ci` show the reason right in the job name; the summaries of `plan` and that job record the same sentence, with a notice `full suite skipped`. `dsh-lib` still runs (for an already-green tree it is only a few seconds of cache lookup).
- **Fails safe:** an API error, an odd answer, an event other than `pull_request` → empty `green_run` → the full suite runs. Only the last 14 days are read, at most 3 pages of green runs and at most 5 candidates checked in depth. The `plan` job now also has the read permissions `actions: read`, `checks: read` (read only).
- **Light gates unchanged**: description, changelog, branch-fresh, Regression are other workflows and still run as before.
- **Two merge gates:** `merged with green Tracy CI` (`check-merged-ci.mjs`) only reads the newest run's conclusion — a skipped run ends `success`, so it is still green. `check-pr-merge.mjs` (step 4 below) exempts the `build check` rows only when the run has the `full suite skipped` job **and** it re-checks the proof itself from the API with the same `proofProblem`: the `plan` job must have exactly one skip record and a `tested tree` record equal to the tree in the skip record; the named run must pass `proofProblem`. Anything wrong → `FAIL`.
- Dry run with real data: `GH_TOKEN=$(gh auth token) node scripts/ci/green-tree.mjs --dry-run --repo TracyHQ/tch --tree <40hex>` prints the decision as JSON. Witnesses: `scripts/test/ci-green-tree.test.mjs`, the `skip:` cases in `scripts/test/check-pr-merge.test.mjs`.

### A fix's new test must go red when the fix is removed — `scripts/ci/new-test-proof.mjs` (since 12/10/2026)

The test suite gains hundreds of cases a week, almost all written by agents, and no gate checks that a new case **can go red**. `check-regression.mjs` only demands a case with a `PASS` line on the branch; `check-pr-description.mjs` only reads the description. The cheapest place to ask is a `fix` PR: the fix is the bug reversed, so a test that ships with it and stays green when the fix is removed does not test the fix.

**What the tool does** with a base/head commit pair:

1. Lists the test files the change adds or edits, and every other file ("the fix"). Files under `test/`, `tests/`, `fixtures/` directories that are not test files are **support files**, kept at head. Case files of `tests/regression/` and `tests/qa/` are a **catalogue** — data for another runner, not `node --test` files, listed separately and not run.
2. Builds **one** copy of head outside the repo (`git checkout-index` from the object store, without reading the working tree), runs each test file with exactly the command of the suite it belongs to — read from the `package.json` **of the tree being run** (`test:workers`, `test:interop`, `test` of the three EmDash templates). A script that changes shape makes that row `not-runnable`; no other command is run.
3. Returns every non-test file to its base version **inside that same copy** (added files deleted, deleted files restored, test files and support files kept at head), and re-runs exactly the files that were green. Before **each** re-run on the copy, and before changing the tree, the copy is brought back to exactly what git describes (see "Each run starts clean").
4. Writes `result.json` + `summary.md` into `--out` (outside the repo), prints a summary to the job summary.

One copy rather than two: measured 12/10/2026 on this repo (75,051 files), one tree is 2.5 GB and takes 35 seconds to write on an APFS disk; two trees eat 70 seconds of the budget before the first test runs.

**Verdict for each test file:**

| Verdict | Meaning |
|---|---|
| `proved` | green at head, red when the fix is removed. `evidence` says what was red: `assertion`, `import-only` (the file or case only **failed to load** a symbol/module — **weaker** evidence, no assertion ran yet; the row says so), or `other` (throw, crash) |
| `unproved` | green in both runs: the file does not depend on the change it ships with |
| `broken` | red at head, in the copy — including a test that cannot load because of its own imports |
| `not-runnable` | with a reason: `time`, needs a browser (e2e suite), needs a database (a case self-skipped for lack of `TEST_DATABASE_URL`), needs a build or a dependency **proven** missing from the copy, has a skipped or `todo` case in either run (the file did not run in full), a path no CI suite runs, an incomplete run |

The whole change is `no-tests` when it adds/edits no runnable test file. Names line up with `scripts/test-trust.mjs` of PR #1245 (`killed` ≈ `proved`, `survived` ≈ `unproved`, `not-covered` ≈ `no-tests`); this tool does not depend on that file.

- 🔒 **Never runs a modified tree in the checkout.** `--scratch-root` and `--out` are refused if inside the repo. The copy is deleted at the end, on error, on timeout and on SIGINT/SIGTERM — after killing the tests' whole process group; failing to delete is a tool error. SIGKILL cannot be caught: the CI job has an `always()` step running `--cleanup` with the same `--scratch-root`, deleting only directories carrying the tool's owner file.
- 🔒 **What the copy may read.** `node_modules` is rebuilt with links: registry packages point to the checkout's installed copy; **workspace packages point to their directory inside the copy**, so tests never import the checkout's product code. A submodule is linked only when the checkout holds it at exactly the commit the measured tree pins; otherwise it is absent, and a test needing it is `not-runnable`, not `proved` by a broken import. Build output not in git is absent the same way. `TEST_DATABASE_URL` is removed from the tests' environment: a modified tree must not point at a database the tool did not build itself, and it builds none (it does not read `deploy/.env`).
- **The copy is its own Git repo** (objects borrowed read-only through `alternates`, `HEAD` at the head commit, the index following the files), because many tests ask git for the list of tracked files: without it `scripts/test/ci-template-data-lane.test.mjs` is red at head through no fault of its own. What tests commit or stage there cannot reach the checkout's repo.
- **Time limit: 180 seconds per commit pair** (`--budget-seconds`), including building the copy and both runs. Enough for the copy plus a few dozen ordinary `node --test` files; and it caps this row's cost as PRs grow. On timeout every unfinished row is `not-runnable: time`, never a pass. Cleaning up the copy happens after the deadline and does not count against it.
- 🔒 **Every flag of the suite except `--test-force-exit`.** That flag ends the test process as soon as the cases finish, without waiting for the results to reach the runner. Measured 12/10/2026, node 24.15 on macOS, ten runs of each kind: a green 200-case file reported only 181 and 190 cases in two runs (exit 0, no warning); a red 200-case file made the runner spin at 100 % CPU in seven runs; without the flag both reported all 200 in every run. The verdict here needs to know **every case ran and none was skipped**, so the trial runs files without that flag. A file that does not exit by itself (a server still open, a timer) is ended by the tool once every registered case has completed and nothing has changed for 5 seconds, only to avoid burning the whole budget — 🔒 **a run ended by the tool is never read as a verdict** (errors arising late in teardown or timers would be missed). That file is re-run exactly as its suite runs it, with `--test-force-exit`, and **that run** is the one judged: it must be whole by `wholenessProblem` like every run (the success/failure summary matching the exit code and the records), **and** report exactly the number of completed cases the previous run saw, because the flag can drop results; missing either makes the row `not-runnable`. In a suite without that flag, a file that does not exit by itself is `not-runnable`. An error thrown after the cases finish but before the 5 seconds makes the flagless run end red by itself and be seen (`broken`). **Consequence for CI in general (outside this change's scope):** the `tests` rows run with the flag, so a green run may not have received the results of a few cases — needs the repo owner to look at separately.
- **A runner with no child processes left but still alive** (the hang shape above; with the flag dropped it no longer occurs in the re-run): the watchdog still stops it after 8 seconds and re-runs the file **once**; the second time the row is `not-runnable`.
- 🔒 **Each run starts clean.** One copy serves every run, so whatever one test writes into the tree (generated files, edited fixtures, a commit) would be read by later tests and by the without-the-fix runs — a cache left by the head run could keep a test green after the fix is removed. Before the copy is re-run or its tree changed (`resetTree`): its `.git` is reset to the saved state, every tracked file differing from the index is checked out again, everything untracked is deleted including ignored files and any `node_modules` created by tests. The only things kept are the `node_modules` the tool built and the submodule paths, and each is forced back to **exactly the list of links recorded at build time** (`restoreMirrors`): an entry a test added, repointed or removed makes the whole directory rebuilt (the previous review round only excluded `node_modules` by name, so a test cache kept in there still leaked into the next run). Not covered: what a test writes **outside the tree** — through a link into the checkout's installation, or into the system temp directory; the copy is not a sandbox. Measured on this repo: about 1.1 seconds each time on a loaded machine (`git diff-files` + `git clean` over 75,051 files); the result records the count and number of files cleaned in `manifest.treeResets`.
- 🔒 **One single definition of "a whole run" (`wholenessProblem`).** A verdict is read only from a run that satisfies **all** of: the reporter wrote its last line; the runner wrote exactly one summary with `success` and counts; the summary's counts match the records (tests, suites, passed, skipped, todo, and failed + cancelled — cross-checked on node 24.15 with suites, nested tests, skip, todo, timeouts and broken hooks: an exact match); the summary's `success` matches the exit code (success ⇔ exit 0); a successful summary has no red record. Anything missing or contradictory → `not-runnable` naming it, never green or red. The three earlier rules each trusted one sign only (the reporter's last line; then the exit code; then the case count) and each let unfinished runs through; now both ordinary runs and re-runs with `--test-force-exit` go through this same function.
- 🔒 **A file that did not run in full is neither `proved` nor `unproved`.** A skipped case or suite, or a `todo` case, in **either run** → `not-runnable` with a reason, even when another case in the file is red with the fix removed: the skipped case may be the very one written for the fix. Every case skipped → `not-runnable` with the skip reason. A `describe(…, { skip })` reports no case inside it, so it is counted as one skip — the 30-PR re-run exposed this: `site-activity-v2.test.mjs` keeps all its database cases in a skipped suite and had been misread as `unproved`.
- 🔒 **Load errors are classified from the error itself, not from guesswork.** The error code, then the error class decides: `ERR_MODULE_NOT_FOUND` and its relatives, `SyntaxError`/`TransformError` (including from dynamic `import()`) are `import-only`, never `other` — compile-only evidence is not enough for `--enforce`. At head, a test that cannot load is **`broken`**; it is `not-runnable` only when the missing thing is **proven** to belong to the copy: a workspace package/submodule that could not be linked, a file present in the checkout but untracked by git (build output), or a package installed in the checkout that the copy does not link. Two places only the message can distinguish, both leaning to the weaker label: a `SyntaxError` from `JSON.parse` is `other`; an assertion that merely quotes a spawned program's "Cannot find module" is `import-only`.
- **Stable results** for the same commit pair: rows ordered by path, fixed classification rules, the copy's path removed from reasons. Seconds are measurements and differ between two runs.

**In Tracy CI** (`tracy-ci.yml`), two new jobs, both **report-only**:

- `test growth (report-only)` — **every non-draft PR**, light runner, installs nothing, runs no tests, no `needs` (so it still reports when `green-tree` skips the whole suite): one line in the summary — the number of test files added/deleted/renamed/edited and cases added/deleted, counted separately rather than as a difference. Cases are counted from the text of the two file versions: each `test(`/`it(` call whose title is a string; a call with a computed title (a variable, a template with `${}`) is counted separately as a "computed registration" because how many cases it yields is only known at run time. This job reports no seconds (nothing is run). It is a separate job on purpose: as a step of `plan`, a tool error would block every `build-check` row.
- `new-test proof (report-only)` — only PRs that `plan` classifies as `fix` with the Regression gate's own `prKind` (title `fix(...)` or branch `fix/…`; output `new_test_proof`). The same bootstrap as a `build-check` row (dsh, `pnpm install`), then the tool runs on `HEAD^1`/`HEAD` of the merge checkout — exactly the pair `plan` uses to list changed files. The summary has the verdict table and the growth line with the **measured seconds** of the added/edited test files in the head run (one process per file, on that runner; not a prediction of how much slower CI gets). Non-`fix` PRs do not get this job: their only cost is the growth line.
- 🔒 `unproved`, `broken`, `not-runnable`, `no-tests` leave the job **green**. The job is red only when the tool itself breaks (git, writing evidence, cleaning up the copy) — exit 1, with no `continue-on-error` hiding it. No gate waits for these two jobs; the `build-check` matrix and every old gate are unchanged.
- **180 seconds is the tool's own budget, not the job's.** The job also pays the same bootstrap as a `build-check` row (fetching the dsh submodule, restoring/building dsh, `pnpm install`) before the tool runs, so the job's total time is that bootstrap plus the tool's actual run time (at most 180 seconds, much less with few files or `no-tests`); that total **has not been measured on a runner** (`timeout-minutes: 30` is a ceiling, not a measurement).
- **Test files needing a database are still `not-runnable` in CI.** The tool removes `TEST_DATABASE_URL` from the environment of every test it runs (and this job does not set that variable either), so even though the runner has a database for the `tests` rows, a case self-skipped for lack of the variable still sends the file to `not-runnable` — no different from a local run.

**The `--enforce` switch** is in the tool, **off by default and switched on in no workflow**. When on, it exits 3 unless at least one file is `proved` by something more than a broken import **and** no file is `unproved`/`broken`; missing evidence (no tests, all `not-runnable`, only `import-only`) is never a pass. Whether to block is the repo owner's decision. Evidence worth having before switching it on:

1. The `not-runnable` rate on real `fix` PRs is low enough that the gate is not red because of the environment (database, build, browser) instead of the tests — the 30-PR re-run recorded in the journal on 12/10/2026 is the first baseline.
2. A sample of `unproved` rows re-read by a person, with the tool right in nearly all of them (the first three rows read: see the journal).
3. The same commit pair gives the same verdict across many runs on a CI runner (no file flipping between `proved` and `time`).
4. A clearly written way out for a fix that cannot have a test running here (infrastructure fixes, fixes only visible in a browser), similar to `feat`'s `Regression: none`.

**What this trial does not prove:** `proved` only says **the test file depends on the change set** it ships with. It does not say each new case catches exactly the fixed bug (an old case in the file going red counts too), does not rule out flaky tests (each run happens once), and does not say the fix is right. `unproved` on a file edited only for tidiness (renames, cases added for unchanged behaviour) is correct and nobody's fault. A fix that is a dependency version (lockfile) cannot show: both runs use the checkout's installed dependencies — the row carries a note when the lockfile changes. Static checks on new cases (no assertion, near-duplicate of an existing case) are out of scope.

```
node scripts/ci/new-test-proof.mjs --base HEAD^1 --head HEAD --out <directory outside the repo>
node scripts/ci/new-test-proof.mjs --growth-only --base HEAD^1 --head HEAD
node scripts/ci/new-test-proof.mjs --pilot 30 --ref origin/develop --out <directory outside the repo>   # re-run N merged fix PRs, from Git history
```

Witnesses: `scripts/test/new-test-proof.test.mjs` (a real Git repo built for each case: `proved`, `unproved`, `broken`, `import-only`, `no-tests`, timeout, cleanup after an interrupt), `scripts/test/ci-new-test-proof.test.mjs` (the workflow wiring), and `scripts/test/new-test-proof-pilot.test.mjs` — the 30-PR re-run, which runs only when `TCH_NEW_TEST_PROOF_PILOT=1` is set.

### Added/edited tests must not add assertions that cannot go red — the `test-quality` gate (since 12/10/2026)

Reading every test file outside `vendor/` (12/10/2026) found 253 cases in 126 files that no product bug can turn red. The `test-quality` gate (`scripts/check-test-quality.mjs`, in `check-all.ts`, so it runs in the `checks` row) blocks the three shapes the assertion's own syntax can tell for sure, **only on what the PR adds**:

- `self-compare` — both sides of `equal`/`strictEqual`/`deepEqual`/`deepStrictEqual` (or the value of `ok`) are fixed in the test file: literals, arithmetic and arrays/objects of literals, a same-file `const` assigned such a value that the file does not modify and does not pass into any call.
- `pinned-constant` — one side is a value imported from a module (read through a property name, no call), the other fixed as above: a product constant compared with a copy of itself. Changing the constant means changing the copy, never catching a bug. Replace it with running the behaviour that uses that constant, or comparing with another value it must match (a second module's constant, a file it must match).
- `machine-path` — a string containing one session's temp directory on one machine (the `claude-<uid>` directory an agent session gets in the system tmp, or macOS's per-user temp directory under `var/folders`; both caught with or without the `private` prefix, exactly the two ways macOS writes them). A made-up home path used as input (`.local/bin/claude` under a fake-named home) is not caught.

A deliberate contract is kept when stated on the spot: `// test-quality: contract <reason>` on the assertion's first line or just above it; without a reason the marker itself is reported. An assertion inside a callback handed to something other than node:test or an array iteration (a test runner's fixture, `step('x', () => assert.ok(true))`) is not examined.

**Only what the PR adds.** For each test file the PR adds/edits, findings in the head version minus findings in the base version (a renamed file is compared with its old path), keyed by rule + the assertion's text; only the remainder is reported. Editing a line next to an old pin passes; re-pinning a constant to a new copy does not. Base: `--base <ref>`; on a PR in CI (`GITHUB_EVENT_NAME=pull_request`) it is `HEAD^1` of the merge checkout (the `checks` row checks out two commits); on another CI event the gate says there is no change to examine and passes; locally it is `git merge-base HEAD origin/develop`, compared with the working tree, including uncommitted and untracked files. An unreadable base, a git error, or a test file that does not parse is RED with a reason. Measured on the branch that added it: 23 test files changed, 1.3 s. A trial scan of all 1,596 test files on `origin/develop` (for calibration only; the gate does not do this): 223 `pinned-constant`, 1 `self-compare`, 1 `machine-path` (exactly the deleted WordPress relay file), 0 unreadable files.

**Different from `new-test-proof` and the content gates.** `new-test-proof` runs a `fix` PR's new tests with and without the fix, reports per file, report-only. This gate runs nothing, examines every PR, per assertion. The `vocabulary`, `language`, `plugin-contracts` gates read product source; this gate only reads test files. **Still a review matter:** regex/`includes` on product source (some are deliberate contracts, syntax cannot tell), tests of helpers defined in the test file itself, tests of code nobody imports, two cases asserting the same thing, and whether a test can run at all.

Witness: `scripts/test/check-test-quality.test.mjs` (a real Git repo built for each case: an old pin kept, new pins/re-pins/untracked files reported, renames, `vendor/` and product files ignored, the PR's base, other events, a missing base, an unparseable file, aliases and shadowing of `assert`).

### Turborepo + a remote cache on R2 decide the tests of PRs into `develop` (since 12/10/2026, approved by Vincent)

**Why.** Measured 12/10/2026 over 247 merges into `develop` (7 days): 57% of PRs fell back to running everything (~40 minutes of runner time each, related-only runs ~7.7 minutes), because the `related-tests.mjs` selector runs everything when it meets a file with no known owner. It also **has a hole the other way**: a PR editing only `packages/cms/tracy-seeder` or `apps/tracy-host` selected **0/361** test files of `apps/tracy-web`, even though that suite reads those two packages through file paths (not declared in `package.json`). The direction was put to the council (Codex gpt-6-astra) twice and settled: cache test results by content hash (Turborepo); do not split the repo.

**How it runs.**
- **Each owner with workers test files is one Turbo task** (43 owners, 47 tasks, 12/10/2026). Workspace packages: a `test:ci` script in the package's `package.json` + the package's `turbo.json`; `apps/tracy-web` is split in three (`test:ci:1..3`, by the timing table `scripts/test-timings.json`). Owners that are not workspace packages (`scripts`, `tracy-joomla-quickstart`, `tracy-wordpress-quickstart`) and the two suites `interop`, `vendor` (dsh-passwords): root tasks `//#test:ci:<name>` in the root `turbo.json`. Every task runs `check-tests.ts --part owner=<owner>[:i/n]` (or `--part interop` / `vendor`), so database, skip list, flags and reporter are exactly as in the full run.
- **Each task's `inputs` are a measurement**: `scripts/ci/turbo-setup.mjs` runs exactly the `node --test` command of **each task** (argv taken from `check-tests.ts`'s exports: each owner, each slice of `apps/tracy-web`, the `interop` suite, and for `vendor` the two build steps + two test commands of dsh-passwords) under `scripts/ci/trace-reads.mjs` (loaded with `NODE_OPTIONS=--import=…`, following child processes too), then `scripts/ci/turbo-inputs.mjs` merges the result into globs: the whole tree for `apps/<app>`, `packages/<group>/<package>`, `vendor/<group>/<tree>`; exact files for files at the root or directly under a root directory (`deploy/.env.example`, `pnpm-lock.yaml`); the parent directory for deeper paths (`.github/workflows/**`); a directory listed recursively becomes the whole directory. The slices of one owner receive the **union** of what they read, so a timing-table change moving a test file to another slice does not leave that slice missing inputs. The dsh submodule cannot be hashed through the parent repo's git index, so a task that reads it has `TRACY_DSH_COMMIT` (the submodule's commit) in its `env`. Every task also depends on the wrapper itself and every file it imports (`MACHINERY`: `check-tests.ts`, `test-timing-reporter.mjs`, `test-database.ts`, `ci/related-tests.mjs` — the wrapper is not measured because it walks the whole repo); sliced tasks add `test-timings.json`. **Never an input**: `.turbo/`, `node_modules/`, `__pycache__/`, `.DS_Store`, the regression runner's logs `tests/regression/.runs/` (these five patterns only take files out of the hash; they accept no read), `.git` directories, and every file git ignores. 🔒 **Reading a git-ignored file is accepted only when it is declared by name in `GENERATED`** (`turbo-setup.mjs`): a generated output (e.g. `packages/cms/tracy-seeder/dist`, `vendor/tracy/dsh-passwords/dist`, `vendor/tracy/dsh-better-sidebar/lib`, the three pages written by `apps/tracy-docs/scripts/generate.mjs`) declares `sources` — the files in git it is built from; a task that reads the output takes those sources as inputs, and the gate is red when a source is missing. **Every declared entry is taken out of every hash** (directories: `<path>/**`; `file: true`: exactly that file), so a row with or without the output hashes the same as `plan` — `ci-turbo-hashes.test.mjs` hashes the tree with and without each entry. There are no rules by directory kind: `__pycache__`, `node_modules`, `.turbo` are not accepted just because of the name; the three `__pycache__` directories the `scripts` suite passes through are declared one by one. `localOnly: true` is for files or directories only a dev machine has (`vendor/tracy/dsh-passwords/.env`; `packages/cms/tracy-seeder/src/data`, where a seeder run from source looks for data before `dist/data` and nothing writes to it): every path of it must be **absent** at measurement time. Every other read of an ignored file — including inside a tree that is an input, such as a `.env` config file — and every read of `.git` is **red**, no longer skipped.
- **An untrustworthy measurement writes nothing and lets nothing through**: a command that cannot start, a non-zero exit (a red test reads less than a green one — only the **red test files** are re-run, up to three times, because the measurement needs one green run of each file and does not judge the tests; a test losing a race on a loaded machine is the test row's business), over 40 minutes, no trace left, or a trace missing the very test files that ran → the whole run stops, the task's log is in the `--artifacts` directory. Hence it needs a database (`--database owned` builds its own container like `check-tests.ts`; by default it borrows `TEST_DATABASE_URL`/the dev cluster) and umask 022 like the runner (an `apps/tracy-host` test compares file permissions `0644`).
- **The `plan` job** (PRs into `develop` only): starts the cache server (`.github/actions/turbo-cache`), **fetches the dsh submodule with the deploy key** (step "Fetch the dsh submodule the task hashes depend on", the same command as the rows; installs and builds nothing), runs `npx -y turbo@<version in package.json> run … --dry=json`, asks the cache about each hash (`turbo-cached.mjs`), lets `turbo-verify.mjs --plan` check the dry-run result before publishing it; `plan-ci.mjs` (`turboRows`) builds up to five rows — `tests web 1/3`, `2/3`, `3/3`, `tests packages`, `tests scripts` — and **turns on only rows that still have at least one task not in the cache**. A PR whose every task is already green for exactly those bytes runs only `checks`. The "tests with the clock moved 400 days ahead" step then runs on `checks` (the row's `clock` flag).
- **An error anywhere fails safe**: missing deploy key, the submodule not fetched within 100 s, the cache server not coming up (then the submodule is not fetched), a dry run failing or taking over 45 s, a result missing one of the tree's tasks / missing internal dependency hashes / the submodule not at the pinned commit, or a task belonging to no row → `TURBO_DRY` is not set (it is written on the **last line** of the step, after the checks) and the plan is as before Turbo (`tests related` / everything).
- **Why `plan` does not let Turbo ask the cache itself**: `turbo run … --dry=json` with a remote cache asks sequentially about all ~1500 entries that have no script (105 s); without the cache it takes ~2 s and still prints every task's hash, then `scripts/ci/turbo-cached.mjs` asks the cache concurrently about the real tasks (HEAD `/v8/artifacts/<hash>`). If the cache server does not come up in a test row → that row runs every task assigned to it.
- **Release PRs (`main`/`staging`), the nightly and manual runs do not read the cache** — that is the net for `inputs` declared incompletely. Since 17/10/2026 they also ask Turbo (the `plan` job fetches the submodule and dry-runs for every event), then `plan-ci.mjs` builds all five Turbo rows with `force`: the rows run `turbo run … --force`, every task really runs, none comes from the cache (results are still WRITTEN, so the nightly warms the cache for the next morning's PRs). Each task audits its own inputs as it runs, so the `checks` of these runs is also only `--structure-only` — before, it re-ran all 47 test suites under the tracer (~19 of the ~23 minutes of a release's `checks`, run 38930622899). `plan` prints the notice `full run` = `turbo`; `green-tree.mjs` and `check-pr-merge.mjs` accept the five-row set as a full run only with that notice. Any Turbo step of `plan` failing → the two rows `tests 1/2`, `tests 2/2` and the full audit in `checks` as before.
- The EmDash rows and `tests e2e` still follow `paths` as before.
- 🔒 **The `turbo-config` gate** keeps three checks: task/script structure, coverage of files read, and git-ignored files that get hashed. Since 13/10/2026, on PRs into `develop` where the planner uses Turbo, each `test:ci` script calls `turbo-setup.mjs --check --task-part <part>`: it runs exactly the test suite once under the tracer, then checks that task's own coverage before returning exit 0. A red test, a missing trace or a read outside the inputs are all red; task mode does not retry, so a flaky test cannot become a green cached result. A cache HIT therefore reuses both the test result and the coverage check. The three measuring files (`turbo-setup.mjs`, `turbo-inputs.mjs`, `trace-reads.mjs`) are in `globalDependencies`; editing the measuring tool makes every task lose its cache, and new keys do not reuse old results that had no audit.
- Only the `checks` row that the planner marks `taskAudits` gets `TRACY_TURBO_TASK_AUDITS=1`; the gate in that row runs `--check --structure-only`: it still checks every task's structure and the ignored-file list, but does not run the tests a second time. Without Turbo data it keeps the earlier full-audit path (`--changed-since HEAD^1` on PRs); releases, the nightly and manual runs with Turbo data have also audited inside each task since 17/10/2026 (section above). The tracer's limits are unchanged: it does not see the contents of files opened by non-Node processes; it only sees the commands and paths on argv. There is no measurement yet of this change's CI time savings.

**Remote cache.** `scripts/ci/turbo-cache-server.mjs` — Turbo's remote cache API (HEAD/GET/PUT `/v8/artifacts/<hash>`) in front of an R2 bucket, SigV4-signed with `node:crypto`, no package dependencies, up in ~0.2 s — runs inside the job on `127.0.0.1:43901` (`.github/actions/turbo-cache`), the bucket in four secrets `TURBO_CACHE_S3_ENDPOINT/BUCKET/ACCESS_KEY/SECRET_KEY` (set 12/10/2026), a random bearer token per job. The key in the bucket is `<team>/<hash>`, like the npm package `turborepo-remote-cache` (used in the trial version, dropped because it pulls in the AWS/Azure/Google SDKs: `npx` took 86 s per job). No standing service, the runner machines are unchanged. Checked on CI (PR #1261): the second run on another runner fetched `dsh-brand` and `seeder` from R2 in 1.2 s.

**When to regenerate.** Adding a package with tests, adding/deleting test files so that an owner appears or disappears, or a suite starting to read files in another tree — all three turn the `turbo-config` gate red and name what is missing:

```
node --import tsx scripts/ci/turbo-setup.mjs                     # re-measure every task, write package.json + turbo.json, then self-check like --check
node --import tsx scripts/ci/turbo-setup.mjs --check             # the gate: structure + coverage + ignored files; writes nothing
node --import tsx scripts/ci/turbo-setup.mjs --check --changed-since origin/develop   # as the gate on a PR: measures only tasks whose inputs the diff touches
#   --database owned     the run's own PostgreSQL container (default: TEST_DATABASE_URL, then the dev cluster, then a container)
#   --accept-red <task>  only when generating, named explicitly: use the trace of a task that is red on this machine (macOS: `//#test:ci:vendor`); the --check gate never accepts it
#   --artifacts <dir>    keep each task's log + trace and turbo-coverage.json (default: a temp directory, deleted at the end)
```

Do not edit `turbo.json` by hand: the structure gate compares it with the generated version, and a hand-added glob is lost at the next generation. When a new ignored build output appears (named by step 2 or 3 of the gate), declare it in `GENERATED` of `turbo-setup.mjs` with the `sources` in git it is built from (`file: true` if it is a single file) and regenerate; if its sources cannot be declared, the test suite must not read it.

**`plan`'s hash must equal the row's hash (fixed 12/10/2026).** `plan` drops a row because of a hash **it computed**; the row computes its hash after fetching the submodule, installing and building. From 12/10 until the fix, the two sides hashed two different trees for the same commit: 12 runs in a row `plan` printed `0 of 47 test tasks are in the remote cache` while the rows themselves got results from the cache (run 38316914525, `tests packages`: 27/39) — no row was ever dropped, and nothing was red. Two causes, measured on one machine, one commit:
- the root `package.json` depends on `@deepseek-ai/*` (`workspace:*`) inside the submodule; `plan`'s checkout had no submodule, so `hashOfInternalDependencies` was empty → **47/47** hashes differed. Fix: `plan` fetches the submodule (above).
- the remaining 2/47 (`//#test:ci:scripts`, `//#test:ci:vendor`) differed because of `vendor/tracy/dsh-passwords/dist/client.js` — a build output, git-ignored, present only in rows; hand-written globs do not follow `.gitignore`. Fix: `OUTPUTS` takes it out of every hash.

After the fix, measured on the dev machine (12/10/2026, same commit): a clean clone with only the submodule added (like `plan`) and a worktree that was installed, built and ran the whole suite twice (like a row) gave **47/47** equal hashes through `turbo-verify.mjs --plan` and then `--compare`. On the runner, the evidence is the log of the Tracy CI run itself.

From now on every run **compares itself** (`scripts/ci/turbo-verify.mjs`), so this class of bug is red the first time it appears:
- `plan` prints each task's hash + HIT/MISS and publishes the output `turbo_manifest` (commit, Turbo version, hashes, HIT/MISS);
- the `checks` row (always runs), after the same install/build steps as a test row and before running any gate, recomputes the hash of **every** task — including tasks of rows that were dropped — and is **red** when a hash differs, a task is missing, or the commit differs (step "Compare every Turbo task hash with the plan job's"); the gates still run afterwards;
- each Turbo row runs `turbo run … --summarize` and compares its tasks with the manifest (step "Compare this row's task hashes with the plan job's", `--row --group <row name> --tasks <the row's Turbo text>`): prints each task `hash cache HIT|MISS (plan: hash HIT|MISS)`. A row's record is evidence only when **complete**: exactly the tasks the row was assigned (derived from the manifest and the row's text), each task once, each with `HIT` or `MISS` from Turbo's summary — a missing, extra or repeated task or a missing cache state is red. A differing hash is red; **a differing cache state is not**: between `plan` and the row, another run may have just written that task (predicted MISS, actually HIT) or a cache entry may not have been fetched (predicted HIT, actually MISS — the task really runs); both are printed with the reason;
- when `plan` falls back to the old plan, the manifest is empty: the two comparison steps print a notice and pass (there is no prediction to check).
- Re-read a PR's evidence from your own machine: `node scripts/ci/turbo-verify.mjs --github [--pr <number>]` (needs `gh`) takes the branch's PR, **refuses if the checkout is not at exactly the revision GitHub holds for the PR** (not pushed yet means nothing to judge), finds the Tracy CI run of that revision, reads the three kinds of lines `TRACY_TURBO_PLAN|CHECK|ROW` in the log and prints: how many tasks `plan` reported in the cache, how many hashes `checks` found equal, what the rows saw. It is red when: the manifest is missing; `checks` did not compare every task; a Turbo row ran without a complete record carrying its name; a task `plan` saw missing from the cache was run by no row; the commit `plan` hashed is not the merge commit of exactly that revision (a `pull_request` run is listed by the branch head but checks out the merge commit); or the run did not end in `success`.

The cost of `plan` (a 5-minute job, runner `tracy-light`): fetching the submodule — history ~220 MB, 14,000 files; the first time on a runner is a full clone, later times only check out the pinned commit (the runner keeps `.git/modules`) — cut off at 100 s; dry run + cache queries cut off at 45 s. Both steps print the seconds they used; **cold/warm times on the runner cannot be measured on the dev machine**, read them in `plan`'s log. A runner whose cold clone does not finish within 100 s will fall back to the old plan every time (with a warning) until someone fetches the submodule for it once.

**`inputs` incomplete because the measuring tool did not see `import { readFileSync }` (fixed 12/10/2026).** `trace-reads.mjs` wrapped `fs.readFileSync = …` but did not call `syncBuiltinESMExports()`, so only the `fs.readFileSync(…)` call style was recorded; almost every test file uses named imports, and the trace held only the imported modules. Measured consequence: editing `.github/workflows/tracy-ci.yml` or `deploy/.env.example` changed **0/47** hashes even though 14 files under `scripts/test/` read them → a PR editing only the workflow received the old green result of the very tests that check the workflow. The measuring tool now syncs named exports, records each path **at the moment of reading** (a child process `kill`ed by a test has no time to run its `exit` handler), follows `node_modules` links back to workspace packages, keeps the tool for child processes given their own `env`, and records the command/`cwd`/repo paths of non-node programs. `interop` and `vendor` were previously **not measured at all** (fixed inputs): now they are measured like every task. Re-measured with the fixed tool: 30/47 tasks have read paths outside the old `inputs` (the largest `//#test:ci:scripts` 10,194/24,716 paths, `//#test:ci:interop` 1,926/1,976, the three web slices 4,336–5,286 each). After regenerating, on the real tree: adding a line to `tracy-ci.yml` changes 2/47 hashes (`//#test:ci:scripts`, `@tracy/dsh-fleet-operation#test:ci`), to `deploy/.env.example` changes 1/47 (`//#test:ci:scripts`).

**Trade-offs chosen, stated plainly.**
- `envMode: "loose"`: tests see every environment variable as before; only the `env` declared in a task goes into the hash.
- CPU architecture does **not** go into the hash: amd64 (AWS) and arm64 (Mac) runners share results, because the tests are JavaScript and native dependencies are pinned by the lockfile. The full, uncached nightly is the net.
- PRs **write** to the cache (the same trust level as anyone with push rights who can read the secret). To make PRs read-only: add `--cache=local:rw,remote:r` to the `Turbo tests` step, and let one job on `develop`/the nightly write.
- `//#test:ci:scripts` depends on 36 trees (the 127 tests of `scripts/test` read almost the whole repo), so the `tests scripts` row runs on most PRs. The root fix: split those tests by what they read (next step).

**Traps hit.**
- Turbo ≥ 2.11 inserts a `turborepo-agent-rules` block into `AGENTS.md` by itself (turning a symlink into a file) when it sees an AI agent running it → the root `turbo.json` sets `"agentGuidance": false`.
- A `.turbo/` log directory not gitignored becomes an input and the hash changes after every run → `.turbo/` in `.gitignore`, and `!**/.turbo/**` in `biome.jsonc` (biome does not read `.gitignore`).
- Measuring the whole `check-tests.ts` process makes it walk the whole repo to count test files, and every task "reads" everything → the generator measures only the owner's own `node --test` command.
- Wrapping `fs.<name>` without `syncBuiltinESMExports()` leaves `import { <name> } from 'node:fs'` pointing at the original function: the tool runs, tests are green, the trace is incomplete — no error says so. `ci-turbo-trace.test.mjs` runs a real `node --test` with named imports to hold this.
- A test that itself runs a child `node --test` must remove `NODE_TEST_CONTEXT` from the child's env: with it, the child runner reports to a parent process that is not listening and exits 0 whatever the tests inside do.
- The dsh-passwords suite (`//#test:ci:vendor`) is **already red on macOS**, with or without the tool (22 tests: binding `127.0.0.2`, deleting under the system temp directory, restoring `cwd`) → on a Mac regenerate with `--accept-red '//#test:ci:vendor'`; inputs written that way are judged by the `turbo-config` gate on the runner (Linux, the suite green). `packages/cms/tracy-quickstart-tools` needs `python3` ≥ 3.12 first on `PATH` (`tarfile … filter=`; Xcode's `/usr/bin/python3` is 3.9).
- The measuring tool must **not** change a child process's environment: an attempt to re-insert `NODE_OPTIONS` for child processes with their own `env` turned `scripts/test/qa-run-agent.test.mjs` red (a test checking exactly which variables a model process sees). A measurement must not change what it measures; such a child process only leaves its command line in the trace.
- A **nonexistent** path the suite probes (and that no input would cover if it appeared) is **reported, not red**: the background scanner in the `apps/tracy-host` suite (`src/mtimes.js`) probes `<entry>/.webroot` under whatever directory it is given, and three measurements in a row probed three different path sets (`apps/.webroot`; `tasks|tch|tests/.webroot`; no path) — a gate red because of them would be randomly red. Nonexistent paths seen at generation still become inputs; what stays open is such a file appearing later without ever having been measured.
- A shell with `umask 077` turns `apps/tracy-host/test/display-locale.test.mjs` red (it compares permissions `0644`), and a red task is an unmeasured task → run the generator with `umask 022` like the runner.

### Auto-merge into develop — `auto-merge-develop.yml`

The `Auto Merge Develop` workflow calls `scripts/auto-merge-develop.mjs` when one of five PR workflows
completes, and sweeps every 10 minutes as a catch-up (at most 20 PRs per run). Only PRs that are open, not Draft, from the TCH repo,
targeting `develop`, with mergeability known to be clean, with no person/team still requested for review and no
latest review requesting changes are considered. It does not merge `staging`/`main` and does not delete the author's branch.

GitHub returns `mergeable: null` while it computes mergeability in the background, and the first read after
develop changes is exactly what starts that computation. The script re-reads the PR up to 4 times, 3 seconds apart;
still `null` → it records `mergeability-unknown` and waits for the next event. The `*/10` schedule is only a catch-up sweep:
GitHub runs it far less often (measured 09/10/2026: runs 3–5 hours apart), so do not rely on it
to rescue a wrongly excluded PR.

For each PR it runs the gate below on the current head, checks PASS with `--expected-head`, re-reads the PR/reviews,
checks that the PASS is still valid right before acting, then calls `gh pr merge --merge --match-head-commit`. FAIL,
UNKNOWN, a changed head, a PR back in Draft, a review request or an expired PASS all mean no merge.

The bot's REST reads prefer the installation token of a separate CI App; only when GitHub returns
403/429 with `x-ratelimit-remaining: 0` and no `Retry-After` does it retry with `GITHUB_TOKEN`.
The helper `scripts/ci/github-read.mjs` accepts only GETs in the source repository (`scripts/ci/ci-repository.mjs`), remembers the reset time within the
process and returns to the App when its quota recovers. Permission errors, network errors, server errors and secondary limits
do not switch tokens. Both sources out of quota is still a read error, not proof of green CI.
The merge command uses an App token with `contents: write`, `pull_requests: write`, keeping the bot identity. The App token
makes the merge emit push/closed events so build/deploy/audit continue as normal; a merge with
`GITHUB_TOKEN` triggers no further workflows. A personal token or an App key serving
customers is never the default. The workflow only checks out reviewed default-branch code, never checks out
a PR or downloads a PR's artifacts. A light runner in the dev lane, a shared concurrency group that does not cancel mid-merge.

**Activation has two conditions; until both are met nothing auto-merges:** GitHub only triggers `workflow_run` and
schedule when the file is on the default branch (`main`); the automation must be brought through the
staging → main path on its own — merging the PR into develop does not mean the bot is on. Then configure
`TRACY_CI_MERGE_APP_CLIENT_ID` (repo variable), `TRACY_CI_MERGE_APP_PRIVATE_KEY` (secret of the separate CI App
installed only for TCH), run `workflow_dispatch` with `dry_run: true`, and then set the repo variable
`TRACY_AUTO_MERGE_DEVELOP=true`. Unconfigured, it is off by default. Every automatic merge still only
targets develop, even though the controlling file lives on main. Once on, older eligible develop PRs are swept too.

**The workflows reading the API share routing:** `Tracy CI` (looking for proof that the same tree is already green),
`CI Before Merge` (reading merged results) and `Auto Merge Develop` (reading the PR/reviews and gating the exact head).
The first two mint a token that only reads `contents`, `pull_requests`, `actions`, `checks`, limited to the
`tch` repo; no private key goes into the repo's scripts. PRs from forks do not mint an App token and still
read with the job token. The auto-merge bot keeps its existing write token, adding `actions: read`, `checks: read`.
The comment reporting a merge with red CI still uses `GITHUB_TOKEN` and does not retry a write with another token.
No personal token goes onto a runner. The App's quota is shared between runners and local machines;
adding runners or minting new tokens does not create more quota for the same installation.

### Check before merging — `scripts/check-pr-merge.mjs` (since 05/10/2026)

**This is a command, not a lock.** The repo is private on the Free plan, so GitHub cannot refuse any merge (the "CI blocks nothing" section above still holds). What was added is a **read-only** command that the person or agent doing the merge runs right before merging, and follows its exit code. It does not merge, push, comment or change the repo; it is not in `pnpm build:check` and is no CI job (it asks about a live PR, something a static gate does not have).

**Why it is needed.** `CI Before Merge` recorded 2 merges without green Tracy CI out of 25 (historical figures supplied for this CI review, not re-measured here) — and it only reports **after** the commit is already on the shared branch. It also accepted **any** `success` run in the list, even when a newer run of the same commit was red, cancelled or still running (reproduced with a test before the fix: `mergedCiVerdict` returned `ok` for the pair "old green + new red").

**The command and its three results:**

```
node scripts/check-pr-merge.mjs --repo TracyHQ/tch --pr <number> --base develop|main
```

| Result | Exit code | stdout | Meaning |
|---|---|---|---|
| `PASS` | 0 | one JSON line (`expectedHead`, `targetSha`, `checkedAt`, each workflow with `runId`/`runNumber`/`runAttempt`) | every condition below holds at the time of reading |
| `FAIL` | 1 | empty | the facts were read and one thing falls short; stderr names exactly that |
| `UNKNOWN` | 3 | empty | GitHub could not be read (missing `gh`, an authentication error, rate limit, network, over 20 s, a response too large or not JSON) or the data is missing / contradictory. **Nothing checked yet** — do not merge, run again; the command does not retry by itself and does not guess |

Wrong arguments (missing, repeated, extra, malformed) exit 2 before any API call.

**What `PASS` requires:**

1. The PR is open, not a draft, in the right repo, targeting exactly the `--base` branch, with its head in the repo itself (a PR from a fork → `UNKNOWN`: a fork's runs cannot be tied to the PR).
2. For **each** of the five workflows that run on PRs — `tracy-ci.yml`, `changelog-check.yml`, `pr-description-check.yml`, `regression-check.yml`, `branch-fresh-check.yml` — read **every page** of the run list of the head commit, keeping only `pull_request` runs that GitHub ties to exactly this PR, head and base branch. Manual runs, the nightly, pushes, runs of other PRs or other commits are not proof. A run that cannot be tied to any PR → `UNKNOWN`.
3. Among those, take the **newest** run = the run whose latest attempt **started last**, read from `run_started_at`; never by list order (the API returns runs within the same second in any order — present in the fixture) and not by `run_number` alone. Reason: re-running a run keeps its `run_number` and `created_at`, only `run_attempt` increases and `run_started_at` resets (read on this repo 05/10/2026: run 2553 attempt 2, created 08:19:46, started 08:30:44) — so an **old** run re-run after the new run went green is the final word on that commit. The chosen run, at that attempt, must be `completed`/`success`. **A newer run that is unfinished or not green does not fall back to an older green run.** If it cannot be ordered, `UNKNOWN`, no guessing: duplicate ids or run numbers, an attempt that is not a positive integer, a missing `run_started_at`, an attempt starting before the run was created, `run_number` and `created_at` contradicting each other in **any pair of consecutive runs** (every pair compared, not only the highest-numbered run against the rest: runs 10/11/12 created at 08:20/08:10/08:30 are refused even though run 12 is both the highest-numbered and the last created), two first attempts starting in reverse run-number order (only a re-run may start late), or two runs both starting last within one second where one of them is a re-run (first attempts in the same second can still be ordered by `run_number`). Every timestamp must be a real date-time: `2026-02-31` or `T24:00:00` are refused even though `Date.parse` accepts them and silently moves them to another day.
4. Read the jobs of exactly that attempt: required jobs must exist and be `success` — `Tracy CI`: `build dsh once for this run`, `plan the build-check rows` and the `build check (…)` rows; the other four workflows: their single job. Which rows are required comes from `planMatrix()` of `scripts/ci/plan-ci.mjs` itself (no second list): into `develop` only `checks` always runs, because a docs-only PR needs no test row; into `staging`/`main` it is **every** row. Every `build check` row present must be green. Jobs outside the required group may be `skipped` (nightly-only jobs), never red. **The only exception (since 10/10/2026):** a run that skipped the full suite because the tree was already green (the job `full suite skipped: …`) is exempt from the `build check` rows after the command re-checks the proof itself — see the `green-tree.mjs` section above.
5. Every job that ran must carry the `tracy-lane-dev` label, for every base branch (since 26/10/2026 PR code never runs on the production lane, [`public-repo-ci.md`](public-repo-ci.md)). The lane label therefore no longer records the base branch; a PR whose base branch changed after CI went green is still caught, because `staging`/`main` require every row (forced Turbo rows count only when `plan` prints `full run`), and `branch-fresh-check.yml` re-runs on `edited` (changing the base branch fires that event).
6. After reading the jobs, re-read **the run list of all five workflows** and choose the newest run again: it must still be the same run, same attempt, same `run_started_at` whose jobs were checked, and still green. A re-run or a new run starting during the reads does not change the PR, head or base branch, so only this read can see it → refused, run the command again.
7. Finally re-read the PR and then the base branch. If the head, state, draft flag, base branch, the PR's `updated_at` (editing a PR starts new check runs) or the base branch's commit changed since the first read → refused.

**Merge exactly the commit that was checked.** The command sequence lives in skill `pr-merge` §3 and is run verbatim by a test with a fake `gh`: `--expected-head` re-reads the `PASS` JSON line and prints the commit only when that line is intact, read from GitHub (not `--fixture`), for the right repo/PR/base branch and no more than 2 minutes old; then `gh pr merge <number> --merge --match-head-commit <commit>`. The result cannot be reused: another push, a base-branch change, a PR edit or letting 2 minutes pass means starting over.

**What this command does NOT guarantee — read before trusting a `PASS`:**

- ⚠ **The base branch can still move on after the last read.** The repo has no merge queue, so the post-merge tree has never been tested anywhere. `--match-head-commit` only pins **the PR's head**. So three old things stay: `git merge origin/develop` + re-running tests before `gh pr ready`, the `branch-fresh` job, and the `pre-push` hook's warning.
- ⚠ **A check run or a re-run starting after the run list is re-read (condition 6) is not seen by the command** — that gap leaves two reads (PR, base branch) plus the time until the merge command.
- ⚠ **Whoever does not run the command is stopped by nothing**: the Merge button on the web, a hand-typed `gh pr merge`, a direct push. So `CI Before Merge` **stays** — it is the only thing that sees those merges, and since 05/10/2026 it also judges the newest run (sharing `newestRun()` with this command, the same ordering by `run_started_at`; red when it cannot order). Also since that date it reads **every page** of a commit's runs (sharing `listAll()`), no longer just the first 20 rows: the API lists by creation time, so an old run re-run late sits at the end of the list — exactly the deciding attempt is what easily falls off the first page. A truncated list, repeated pages or a mismatched `total_count` → red with a reason; it never takes the part it could read as the whole.
- Conditional rows (EmDash, e2e) absent from a PR into `develop` are accepted on the strength of the `plan` job being green in the same run; the command does not recompute the PR's diff itself.
- The command does not read the PR's conflict state; `gh pr merge` refuses by itself while conflicts remain.

**What was checked with what, and what was not.** The behaviour is tried with fixtures saved from real GitHub responses (`scripts/test/fixtures/pr-merge-api.json`, PR #893 on 05/10/2026, fields trimmed) and a fake `gh` that records every argv (`scripts/test/check-pr-merge.test.mjs`, `scripts/test/check-merged-ci.test.mjs`, run in `pnpm test:workers`): every call is `gh api --method GET`, and after `FAIL`/`UNKNOWN` `gh pr merge` is not called. **Not checked:** a real merge; `run_started_at` resetting after a re-run has only been read on one real run (2553 above), the re-run cases in the tests are data built from fixtures; GitHub really refusing when `--match-head-commit` mismatches; the `CI Before Merge` job really running on Actions with the new code. Workflow names, job names and lane labels are pinned to the workflow files by tests — changing them means editing `WORKFLOWS` in the script and the fixture in the same PR, never dropping the requirement to get green.

**Follow-up over the next 25 merges.** There is no measurement of time saved; the only figure is the 2 in 25 above. After this change lands on `develop`, measure **the next 25 PRs merged into `develop` or `main`, by any path** (this command, the web button, a manual push) — taken by `merged_at`, no cherry-picking:

| Column | Taken from |
|---|---|
| PR · merge path | `gh pr list --state merged`; whether a saved `PASS` line exists |
| head at merge time | `head.sha` of the merged PR |
| target at merge time | the merge commit's first parent (`merge_commit_sha^1`) |
| run / attempt and state of each workflow at merge time | **reconstructed at `merged_at` for every merge, including those with a `PASS` line**: among the head's `pull_request` runs, the run whose attempt **started** last before `merged_at` — judged by the start and end times of the **attempt** at merge time (started before `merged_at`; ended before then → its result, not yet ended → unfinished), not by when the run was created: an old run's attempt may start after the merge. The `PASS` JSON line is only **cross-checking** evidence, not a substitute for reconstruction: it speaks of when the preflight read, and a check run or re-run may start after that and before the merge (the gap above). A `PASS` differing from the reconstruction (another run, another attempt, another state) → take the reconstruction and record the difference. If the attempt that was newest at merge time cannot be reconstructed → `unknown`, even with a `PASS` line |
| classification | `qualifying` = all five workflows meet conditions 2–6 at merge time · `nonqualifying` = at least one does not · `unknown` = cannot be reconstructed (a run re-run after the merge so the attempt at merge time can no longer be read, missing API data) |

`unknown` is counted separately and does **not** count as qualifying. The results go into a `tasks/` file of whoever measures, together with the number of red `CI Before Merge` runs in the same period; collecting all 25 merges happens after this change is merged.

### The `lint` gate reports per-part timings and cache state (since 04/10/2026)

Before, there was only one number for the whole gate (median 61.3 s, maximum 93 s in the early-October CI sample) and one line per tsc project. `scripts/check-lint.ts` now prints the lines below as well. **This is a report, not a decision**: no command, flag, order, parallelism or exit code depends on them; the three layers of protection (oxlint, typecheck, format) run and go red exactly as before. The behaviour is held by `scripts/test/check-lint.test.mjs` (run in `pnpm test:workers`).

| Log line | Meaning | Limit |
|---|---|---|
| `check-lint: time — oxlint: N ms (ok\|FAILED)` | wall time of the oxlint command | — |
| `check-lint: time — typecheck (whole stage): N ms (…)` | from the start of the first project to the end of the last | differs from the sum of the `tsc -p …` lines because projects run in parallel |
| `check-lint: time — format:check (biome format + biome lint, one figure): N ms (…)` | the whole `format:check` script | **one** figure for the two biome commands plus `pnpm` start-up; splitting it means running them separately, i.e. changing the gate |
| `check-lint: time — total: N ms (ok)` | the whole gate, printed only when green | excludes the start-up time of `tsx` and `check-all.ts` |
| `check-lint: cache — restore: exact \| prefix \| miss \| unknown` | what the `Restore the typecheck build-info` step reported through the three outputs `cache-hit`, `cache-matched-key`, `cache-primary-key` | only says a directory was unpacked, **not** that tsc could use it. `miss` = only `cache-primary-key`, the other two outputs empty (exactly what `actions/cache` v6 writes when nothing is found). `unknown` = no outputs (a personal machine), a key not in the workflow's `tsc-<40 hex>` shape, or three values that contradict each other (e.g. `cache-hit=false` with no matching key) |
| `… [build-info before start: present, unvalidated \| missing \| unknown, … \| disabled]` at the end of each `tsc -p …` line, and the summary line `check-lint: cache — build-info before start: A present (unvalidated), B missing, C unknown` | one `lstat` of the project's build-info file, taken **right before** that project's tsc starts | does not open the file: `present` only means "a regular, non-empty file", **not** proof that tsc reused it. Symlink, directory, FIFO, empty file, an `lstat` error other than `ENOENT` → `unknown`. `disabled` = no `TRACY_TSC_CACHE_DIR`, or the sequential path (`pnpm typecheck`, no `--incremental` passed) |

- A red step still prints its own `time` line (`FAILED`) before the `step "…" is red` line; the steps after it do not run, so they have no line. This includes a step dying from an error rather than an exit code: an unreadable or broken `package.json`, and a project's tsc failing to start (that project counts as `FAILED`, the other projects still run).
- ⚠ The build-info state is a snapshot **before** the run because tsc rewrites that file: after a cold run every file is present, so looking at the directory after the run cannot tell cold from warm.
- **Comparing cold/warm locally** — two consecutive runs with **the same** new cache directory, nothing else changed. Assign the directory to a variable once: calling `mktemp` in each command gives each run its own directory, i.e. two cold runs.

  ```
  CACHE="$(mktemp -d)/tsc"
  TRACY_TSC_CACHE_DIR="$CACHE" pnpm exec tsx scripts/check-all.ts --only lint   # run 1 (cold): N missing
  TRACY_TSC_CACHE_DIR="$CACHE" pnpm exec tsx scripts/check-all.ts --only lint   # run 2 (warm): N present
  ```

  Read: (1) both runs must reach **the same verdict** — warm green and cold red, or the reverse, is a cache bug, not a saving; (2) compare the `typecheck (whole stage)` line of the two runs, and each `tsc -p …` line to see which project benefits; (3) `oxlint` and `format:check` do not use build-info; their difference between the two runs is machine noise.
- 🔒 **Before accepting a further optimisation of `lint`** (splitting the job, adding caches, changing parallelism): it needs an equivalent cold/warm verdict **and** a real-time benefit measured on CI — the `checks` job duration, the whole Tracy CI run duration, the `restore: exact/prefix/miss` rate, and runner memory. The lines above only provide the time and cache part; **runner memory has no measurement yet**, and measurements on a macOS machine say nothing about the runner. `lint` stays in the `checks` job: splitting it out adds a checkout, an install and a runner request.

- 🔒 **But a runner can die while its machine and container look fine — silently.** A runner can go `offline` while `docker compose ps` still shows the container "Up"/`running`; the only signs are its container log stopping and GitHub reporting `status=offline`. `tracy-dev-01` is the **only** `tracy-dev` runner, so every `deploy-dev`/`deploy` job then waits (runs stuck 16–20 h, looking like a busy queue, none red for code reasons). Ask GitHub, not docker:

  ```bash
  gh api repos/TracyHQ/tch/actions/runners --jq '.runners[] | "\(.name) \(.status) busy=\(.busy)"'
  ```

  On `offline`: `ssh root@<that runner's machine — table above> 'cd /opt/tracy-runner && docker compose restart <service>'` (an offline runner has no job to interrupt); ~25 s later it logs `√ Connected to GitHub` and takes the waiting work. With `cancel-in-progress: false` a stuck run **holds its concurrency group** and everything queues behind it, so clearing the stale queue is part of the fix.
