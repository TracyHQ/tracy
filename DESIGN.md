## 0. Two modes, and how to tell which one you are in

TCH's CSS rules are **not one set but two**, and choosing the wrong set is the costliest failure
here. Only one question decides: **who owns this page's `<html>`?**

| | **Mode A — Tracy's page** | **Mode B — plugin inside the dsh page** |
|---|---|---|
| Who owns the document | Tracy | dsh |
| Where | `@tracy/design` (Vite bench), Storybook, and pages generated by the Worker | `@tracy/dsh-chat-input`, `@tracy/dsh-settings`, `@tracy/dsh-my-sites`, `@tracy/dsh-site-tabs` — i.e. **the product surface** |
| Tailwind | **Yes** — Tracy owns the reset | **NO** — bringing a second reset breaks the host's UI |
| How classes are written | utilities (`bg-card`, `rounded-lg`) | plain CSS, `tv-` prefix |
| Colour source | `tokens.css`; dsh's aliases are absent, so **the fallback decides** | `--dsw-alias-*` with a fallback; the aliases are present, so **the alias wins** |
| Dark switch | `.dark` / `:root[data-theme="dark"]` | `[data-ds-dark-theme]`, set by dsh itself |

🔒 **The product surface is mode B — changed on 01/09/2026, see [`ADR 0004`](docs/adr/0004-dsh-is-the-shell.md).**

This section used to say the opposite: *"the direction is mode A, TCH builds its own `apps/web`"*.
That sentence died when **dsh became the shell**. Tracy's outer SPA is gone — the
`packages/web/tracy-frontend` package was removed from the repo on 05/10/2026 — and Tracy's tabs now
**live in dsh's sidebar**. So what customers see every day has **dsh owning `<html>`**, and follows
rule set B: no reset, no Tailwind, `tv-`-prefixed classes.

**Mode A is not dead, it changed role.** It is where you *draw before you code*: the `@tracy/design`
bench, Storybook, and the pages the Worker generates itself (sign-in gate, handoff page). There
Tracy owns the document, so it is **completely free**.

⚠ **The trap when moving from A to B.** A screen drawn in mode A with Tailwind utilities **does not
port straight** into a plugin — it has to be translated into plain `tv-`-prefixed CSS. And when
borrowing a layout from a shadcn template, borrow only **what is inside the card** (lists, badges,
buttons); **the sidebar and header belong to dsh**, and drawing over them gives two stacked layers of
navigation — exactly the bug measured on 30/08.

⚠ **Worker pages are mode A but have NO Tailwind.** This is where the table above lumps two different
things together: Tracy owns the document, but that page cannot load `tokens.css` and has no build
step, so tokens are redeclared **by hand** — the contract for that redeclaration is
[`docs/references/page-shell-tokens.md`](docs/references/page-shell-tokens.md). Do not read "Tracy
owns the reset" as "utility classes are allowed here". For the same reason `.dark` does not reach
them: Worker pages switch to dark with `prefers-color-scheme`, so the theme switch in Storybook has no
effect on them.

🔒 **Do not rebuild an outer SPA.** `packages/web/tracy-frontend` (the old SPA) and
`packages/web/tracy-shell-routes` (deep routes for the model where dsh served the SPA) were removed on
05/10/2026; new surfaces go into dsh in mode B.

## 1. Tokens

`tokens.css` declares tokens **under shadcn's standard names** (`--background`, `--primary`,
`--sidebar-*`), each shaped like:

```css
--background: var(--dsw-alias-bg-base, oklch(1 0 0));
```

dsh's alias wins when present; the shadcn value stays as the fallback, so components render **outside
dsh too**. 45 variables are mapped this way.

This is why we do **not** use custom names like `--tracy-*`: keeping the shadcn names means any block
copied from shadcn lands in the right place.

### 1.1 Three selector layers — read carefully, this is the subtlest part of the file

| Selector | Role |
|---|---|
| `:root, body` | Mapping + **LIGHT** fallback |
| `[data-ds-dark-theme], .dark, :root[data-theme="dark"]` | **Same mapping, DIFFERENT fallback** — the fallback here is the **DARK** value |
| `@theme inline` | Generates `--color-*` for Tailwind |

The mechanism, stated once clearly:

- **Inside dsh** — `--dsw-alias-*` is present and always wins, so the dark block *changes nothing*.
  dsh already switches light/dark through those same aliases. `[data-ds-dark-theme]` is the signal
  dsh actually emits.
- **Outside dsh** (the `@tracy/design` bench on Vite) — the aliases are empty, **the fallback
  decides**. So `.dark` and `:root[data-theme="dark"]` are **not dead code**: they are mode A's dark
  switch.

CSS cannot say "if the variable is undefined then…" — `var(--x, <fallback>)` **is** how you say it,
and this is using it for exactly that purpose.

🔒 **`tokens.css` and `dsh-bridge.css` NEVER stand in one document as CSS together.**
`tokens.css` reads the aliases; `dsh-bridge.css` declares the aliases from the tokens. Loading both
makes a CSS variable cycle, and CSS computes every variable in a cycle as **empty** — measured
03/09/2026: light looked fine because the canvas was white, dark gave a white body with black text.
Since 03/09 the bridge is a **mapping table**: `@tracy/dsh-brand` turns it into a constant
`{ light, dark }` table at build time and hands it to dsh's `ctx.theme.overrideTokens` —
[`ADR 0007`](docs/adr/0007-tracy-skin-through-ctx-theme.md).

🔒 **Declare on `:root, body`, NOT just `:root`.** `var()` is resolved **where the variable is
declared**, not where it is used. dsh sets `--dsw-alias-*` on `<body>` (measured 30/08: empty on
`:root`, `#151517` on `body`). A `:root`-only block resolves **every** alias as empty, takes the light
fallback, and passes that light value down the whole tree — **even while dsh is in dark mode**. Real
symptom seen: a white nav next to dsh's dark cards, text fading out.

### 1.2 Token rules

- **No hard-coded colours.** No `#hex`, `rgb()`, `oklch()` in components. Get this wrong and dark
  mode breaks **silently**: it still shows, just in the wrong colour.
- **Brand is NOT mapped — the opposite direction is right.** `--primary` and `--ring` keep
  **terracotta `oklch(0.588 0.136 37.4)` (#bf5b3d)** instead of taking `--dsw-alias-brand-primary`.
  Inside dsh, `@tracy/dsh-brand` is the one that sets `--dsw-alias-brand-primary` (and `--primary`
  inline on `<body>`) from the colour the user picks in Settings › Primary color; the default is that
  same terracotta (`DEFAULT_PRIMARY`, `packages/brand/tracy-brand/src/shared/settings.mjs`).
  **Decided 14/09/2026: terracotta is the primary of the whole system** — primary buttons, the send
  button, ring, selection borders; Tracy blue `#5b8def` is now only a swatch. ⚠ The pages `tracy-web`
  draws itself (`lib/page-shell.js`: login, join, team) and `workers/` still declare Tracy blue by
  hand — not changed yet. Background, text, borders and states are the opposite: they **must** blend
  into the host page.
- **Use matching background/foreground pairs.** `bg-card` goes with `text-card-foreground`. Mixing a
  background from one group with text from another is how you create something unreadable in one of
  the two themes.
- **A new token goes into `tokens.css` IN THE SAME change.** A `var(--tv-glass)` that does not exist
  resolves to **empty**, and an empty `background: ` is transparent, not an error.
- **Alias names must be REAL.** A mistyped `--dsw-alias-*` is hidden by the fallback: the screen looks
  normal, but that colour **stays put when switching light/dark or turning on a skin**. No error, no
  warning, never caught by eye. → guarded by `scripts/check-dsh-tokens.ts`, which reads the real list
  from the installed `@deepseek-ai/dsh-client-ui-theme`. On 30/08 it immediately caught two names that
  do not exist (`--dsw-alias-semantic-danger`, `--dsw-alias-semantic-warning`) and had lived there since
  the plugin was born, behind two very plausible red and orange fallbacks.

## 2. Components

- **Take them from `@tracy/ui`.** 24 shadcn-style primitives (base-nova) + `platform-glyph`,
  `settings`. If one is missing, **port it into `packages/ui/tracy-ui`** following the current
  standard — use `dropdown-menu.tsx` as the model. **Do NOT copy Radix from
  `vendor/tracy/shadcn-admin`**; it is only a style/layout reference.
- **Merge classes with `cn()`**, not string concatenation. `cn` uses tailwind-merge, so a later class
  wins over one of the same group — with plain concatenation the caller's `className` "does not take"
  and there is no error. Counter-intuitive: `flex`, `hidden`, `block` are **in the same display
  group**, so `cn('flex', cond && 'hidden')` yields `hidden`, not `flex hidden`.
- **Every icon-only control needs an `aria-label`.** Controls with text do not.

## 3. Mode B CSS rules (plugins inside the dsh page)

- **Do not bring in Tailwind's RESET.** That page has its own reset already; adding another breaks the
  host's UI. Two valid ways, and since 03/09/2026 the second one is the default for surfaces with
  components:
  1. Plain `tv-`-prefixed CSS, embedded as a string at build time and injected through `ctx.effect` —
     for small surfaces that use no components (`chat-input`).
  2. **Tailwind WITHOUT preflight** + `@tracy/ui` components: `@import 'tailwindcss/theme.css'`
     and `utilities.css` with `source(none)`, `@source` pointing only at the package and
     `@tracy/ui/src`, the result baked into the bundle via `define` — the recipe is in
     `packages/ui/tracy-settings/src/client/settings.css` and its `scripts/build-client.mjs`.
     `dsh-settings`, `dsh-sidebar`, `dsh-add-site`, `dsh-my-sites`, `dsh-site-tabs`,
     `dsh-design-inspiration` take this path. It is the only way for a plugin's insides to be the
     library's components instead of a hand-copied near-lookalike.
- **`tv-` prefix, scoped under one root** (`.tv-root-composer`). Without a prefix your classes
  collide with dsh's.
- **Hang on `var(--dsw-alias-*, <fallback>)`, always with a fallback.** The view follows dsh's
  light/dark switch without needing to know how it is switched.
- **Declare the variables on EVERY root the plugin renders**, not just one. Each slot occupant mounts
  at a different place in the dsh tree, so a variable block declared on one root does **not** reach
  another. An empty `var()` is not a fallback — it is nothing.
- **Do not hang on dsh's hashed class names** (`pI_x6G_sidebarCol`). Match on the readable tail:
  `[class*="sidebarCol"]`. The hash changes every time dsh is rebuilt.
- **Overriding a `--dsw-alias-*` is cheaper than redrawing what it paints.** dsh's
  `packages/client/ui-chat` is fully tokenised. Before adding a rule, check whether dsh already paints
  that spot.

### 3.1 Two traps of the Tailwind-inside-dsh path — measured 15/09/2026 on the Add site tab

Both give the same symptom: **the class is right in the JSX, Storybook (mode A) draws it right, and on
the dsh page it is wrong** — with no error line.

1. **Nine Tailwind sheets on one page, the last injected wins.** Every plugin on the Tailwind path
   injects its own full utility sheet, in the same `@layer utilities`. A CSS layer is global to the
   whole page, so inside that layer only source order is left: `.rounded-lg` and `.border` from a
   plugin injected LATER override `.rounded-r-none` / `.border-l-0` from a plugin injected EARLIER,
   even on the same element. Measured: `dsh-add-site` injected earliest (#102 of 9), the address
   suffix box lost its square corner and grew a double border. How to avoid it: **do not rely on a
   "modifier" utility that only your plugin uses** (`border-l-0`, `rounded-r-none`). Either use a
   component that already packages that shape (`InputGroup` — its children carry `rounded-none
   border-0`, tailwind-merge drops the contested class so there is nothing left to lose), or write a
   rule scoped under the plugin root (`.tas-root …`) — higher specificity, no sheet can override it.
2. **A component's `dark:` variant is not replaced by `cn()`.** `Button variant="outline"` carries
   `dark:border-input dark:bg-input/30`; tailwind-merge only replaces classes **with the same variant
   prefix**, so a bare `border-primary` wins in light and loses in dark. For a colour that holds in
   both themes, write the pair: `border-primary dark:border-primary`. Measured: the selected platform
   chip wrote `border-foreground/30`, and in dark the border computed to `--input` — invisible.

And a Chrome trap, not a Tailwind one: **form history suggestions paint the autofill background on the
`<input>` itself**, so an `InputGroup` (input + suffix) turns two-tone. A field that is not form
history (site name) gets `autoComplete="off"`; add-site's `styles.ts` also has a `:-webkit-autofill`
rule that cuts that background under `.tas-root` to be safe.

## 4. Layout

A site screen has **one header row per pane, all three aligned** (Chat · Changes · Preview). This is
a pattern, not a suggestion: a pane that draws two rows breaks that horizontal line. Standard height
`h-11` (44px).

## 5. Do / Don't

**Do**
- Port the JSX from `@tracy/design` when that view is already built
- Use `cn()` for every conditional class
- Put an `aria-label` on icon-only controls
- Add a new token to `tokens.css` in the same pass as its first use
- Hide controls that have no backend yet, or `disabled` + "Coming soon" — **do not draw dead buttons**
- 🔒 **On-screen text: as little as possible** (25/10/2026 — agents drawing screens tend to write long
  and add needless sentences). Any word the user can do without, cut.
  - A title is a phrase; no subtitle when the title already carries the meaning.
  - A button is a verb (plus a noun if needed), with no explanatory sentence.
  - A field has at most one hint line, about 10 words; anything that needs a longer explanation goes
    in a tooltip.
  - Empty state: one sentence saying what is missing, plus one button.
  - Do not repeat what the user already sees right next to it (if the label is "Email", the hint does
    not say "Enter your email").
  - With no real data, leave it empty; do not write text to fill the space.
  - On-screen words still come from [`vocabulary.md`](docs/references/vocabulary.md); this rule only
    says *how many*, not *which*.
  - When handing a drawing back, write one line for each piece of text you cut so the reviewer sees
    it. No CI gate catches this.

**Don't**
- Hard-code `#hex` / `rgb()` / `oklch()` in a component
- Name a new token outside `tokens.css`
- Bring Tailwind into mode B
- Copy Radix components from `vendor/tracy/shadcn-admin`
- Invent data for a part that has no endpoint (invented is **worse** than empty — users trust it)
- Hang on dsh's hashed classes
- 🔒 **Draw a halo/shadow around a field on focus.** Settled 29/09, restated 05/10/2026 on the Invite
  people screen: focus (mouse click or Tab) is **a border colour change, one 1px stroke**, nothing
  more. Banned in every mode: `ring-2`/`ring-3`/`ring-ring/50` and any `ring-*` thicker than 1px,
  `box-shadow: 0 0 0 Npx …` in a translucent colour, a thick `outline` used as a halo. Need one more
  distinction (e.g. a selected card reached by Tab)? **Change the stroke colour**, do not add an outer
  layer. Why: the shared `@tracy/ui` components (input, textarea, select, button) already have only
  `focus-visible:border-ring`; halos only get in through hand-written CSS, and the §6 table itself
  once taught `ring-ring/50 ring-3`, so it spread (the Invite people email field, the theme thumbnails
  in Settings). No CI gate catches this, so **grep yourself before pushing**:
  `git grep -nE "(focus|focus-visible|focus-within):ring-(2|3|\[)|ring-ring/|:focus[^{]*\{[^}]*box-shadow: *0 0 0 [2-9]px" -- packages apps ':!packages/cms' ':!**/dist/**' ':!**/test/**' ':!packages/**/lib/**'`
  must come back **empty** (measured 05/10/2026). `ring-2` for a *selected* / *dragging* state is not
  focus, so it is not caught.
  (`packages/cms` holds customer site templates, which follow the customer's design and are outside
  this rule.)

## 7. Mode C — HTML returned directly by the Worker, and the "looks like the design system" rule

Modes A and B both run in a page with Tailwind. **Mode C does not**: `workers/` returns HTML straight
to the browser, with no build step, no Tailwind, and no way to load CSS from another host. So it
writes CSS by hand and names its own classes.

That is where the design system drifts, and on 01/09 the exact reason was measured:

| | How it is written | The same card |
|---|---|---|
| shadcn-admin / `@tracy/ui` | utilities composed per element, **no semantic classes** | `flex flex-col gap-6 rounded-xl border bg-card py-6 text-card-foreground shadow-sm` |
| `workers/` | 45 self-named semantic classes | `.card` `.auth` `.note` `.sub` `.pill` `.perm` |

**The two sides share not a single name.** After the tokens were unified (see
[`docs/references/page-shell-tokens.md`](docs/references/page-shell-tokens.md)) they share **colours**
— but the *shape* is still completely free: padding, gap, radius, shadow, type scale. That is why a
page can have the right tokens and still not look like the design system, and why "fix the tokens" is
not enough.

### 7.1 The three-part rule

The token contract only guards the first part. Without the other two it still comes out wrong —
proven on 01/09.

**Part 1 — Tokens: names and values.** See `page-shell-tokens.md`.

**Part 2 — Components: copy the RECIPE, not just the colours.**
Every semantic class in the Worker must carry **the utility recipe it translates**, taken verbatim
from the matching `@tracy/ui` component. Written down, the two sides **can be compared**; not written
down, they can only be compared by eye, and the eye cannot tell padding 22 from 30.

```
/* .card  ⟺  Card from @tracy/ui
   flex flex-col gap-6 rounded-xl border bg-card py-6 text-card-foreground shadow-sm */
```

**Part 3 — Verification: SOMEONE MUST LOOK, next to the reference screen.**
UI work is not done when it "compiles" or "tests are green". It is done when it has been rendered and
eyes have seen it.

**Anyone's eyes will do — agent or person — but rendering + opening is the agent's REQUIRED step**
(settled 01/09). An agent may not conclude "matches the design system" from reading code; it must
build the page and open it, then either inspect it itself or hand it to a reviewer. What is banned is
**skipping the render step**, not who looks.

```bash
node -e "…" > /tmp/preview/login.html && open -a "Google Chrome" /tmp/preview/login.html
```

🔒 **This is the part most often skipped, and the most expensive.** On 01/09 an agent wrote "matches
the design system" after **only reading the code** — right tokens, green tests, and the page looked
like nothing of the sort. No rule about colours catches that.

### 7.2 Deliberate deviation must be WRITTEN DOWN

Mode C lacks two things the design system takes for granted: **no script** (ADR 0034) and **no build
step**. So some components cannot be ported as-is, and that is acceptable — on one condition:
**write the reason right at the deviation.**

The existing example, and a good one: the code field on `/login` uses **one box** instead of the
bench's **six boxes**. The comment in place says six boxes need a script to move the cursor and handle
paste, and this surface has no script — so six boxes there would mean typing each key separately, and
pasting would break.

A deviation that is not written down means that next time nobody can tell a **decision** from a
**bug**, and someone will "fix it to match the bench" and break something that was right.
